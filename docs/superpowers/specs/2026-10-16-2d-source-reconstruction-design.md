# 2D 원본 재구성 비교 설계

## 목적

생성한 2D 에셋 묶음(바닥 타일·오브젝트·원경 배경)으로 원본 구도를 얼마나 똑같이 다시 만들 수 있는지, 사용자가 제작 계획 검수 화면에서 직접 판단할 수 있게 한다. 사용자의 말로는 "원본 구도를 타일로 얼마나 동일하게 만들 수 있는지를 보고 싶다"이다.

판단 근거는 원본 위에 겹친 재구성 결과다. 재구성은 바닥 타일을 원본 전체에 반복해 깔고, 벽·지붕 같은 구조물은 오브젝트로 원본에 나오는 모든 자리에 올려서 만든다.

## 현재 상태

- [PR #16 기록](../../verification/2026-10-16-2d-source-compare.md): `SpriteSourceCompare.tsx`가 계획 검수와 별도인 패널에서 각 에셋의 현재 기준 이미지를 ROI 한 자리에만 놓는다. 타일도 한 칸만 놓는다.
- 2026-10-16 일회용 시안(작업 `300f237d`, isometric 128×64 타일 8종, 원본 1536×1024)에서 확인한 사실:
  - 칸마다 원본과 가장 비슷한 타일을 자동으로 고르는 방식은 도로·인도 같은 바닥에서 쓸 만했다.
  - 외벽·차양·셔터가 타일로 생성되어 있어 반복하면 작은 건물이 흩어진 들판처럼 보였다. 세로로 선 구조물은 납작한 타일로 표현되지 않는다.
  - 구역 평균색 기반 칸별 차이 지도는 실제 차이보다 너그러워 판단 근거로 쓸 수 없었다.
- 분석 프롬프트 [SeedPrompts.cs](../../../apps/backend/Noxtend.Infrastructure/Llm/SeedPrompts.cs) `AnalyzeSpritesV3`/`V4`는 벽을 타일로 분류하고, 오브젝트는 대표 하나의 위치만 돌려주게 한다. 지붕·차양은 이미 오브젝트로 분류하라고 되어 있다.
- 계획은 `SpriteAssets.PlanJson` JSON 열에 저장된다(`SpriteAssetPlan` 레코드). 수정은 `PUT /api/jobs/{id}/sprites/plan` 하나다. `PipelineJob.Sprites.cs`의 `GenerationChanged`가 재생성·승인 무효화 대상 필드를 정한다.
- 3D 파이프라인에는 한 파츠를 여러 자리에 놓는 `placements`(1~20개)가 있다. Frontend [PartsOverlay.tsx](../../../apps/frontend/src/features/screens/background/PartsOverlay.tsx)는 한 대상에 여러 박스를 그릴 수 있고, 2D 계획 검수도 이 컴포넌트로 ROI를 그린다.

## 범위

### 목표

1. **재구성 겹쳐 보기**: 제작 계획 검수가 끝난 뒤, 계획 검수 화면의 원본 이미지 위에 재구성 결과를 투명도 슬라이더로 겹친다.
2. **바닥 타일 반복 채우기**: 원본 전체를 격자 칸으로 나누고, 칸마다 원본 그 자리와 가장 비슷한 생성 타일을 자동으로 골라 채운다.
3. **오브젝트 여러 자리**: 오브젝트 에셋은 원본에 나오는 모든 자리(`placements`)를 가진다. AI 분석이 자리를 찾고, 계획 검수에서 사람이 추가·삭제·이동으로 고친다.
4. **분석 프롬프트 개정(V5)**: 벽도 오브젝트로 분류하고, 오브젝트마다 모든 자리를 돌려준다.

### 하지 않는 것

- 자리 정보나 타일 배치를 ZIP·manifest로 내보내지 않는다. 재구성은 판단용 화면이다.
- 일치율 점수·합격 판정·칸별 차이 지도를 보여 주지 않는다. 시안에서 평균색 지표가 실제보다 너그럽게 나왔다.
- 이미지 매칭으로 오브젝트 자리를 자동 탐지하지 않는다. 자리는 AI 분석과 사람의 수정으로만 정한다.
- 기존 작업의 역할·자리를 자동으로 바꾸지 않는다. 기존 작업은 계획 검수에서 사람이 역할을 바꿀 수 있고, 그때의 재생성은 기존 규칙을 따른다.

### 실패로 보는 것

- 자리만 고쳤는데 이미지 재생성, 승인 무효화, 현재 ZIP 표시 변경이 일어나는 것. 유료 호출이 늘어난다.
- 재구성이 원본과 실제보다 더 닮아 보이게 만드는 표시. 예를 들어 빠진 에셋을 숨기거나 근거 없는 점수를 띄우는 것.
- 운영자가 수정한 분석 프롬프트 버전을 덮어쓰는 것.

## 설계

### 1. 재구성 겹쳐 보기 (Frontend)

- 위치는 `SpritePlanReview.tsx`의 원본 이미지다. 제작 계획이 승인되어 `phase`가 `planReview`가 아니고 기준 이미지가 하나 이상 있을 때 재구성 층과 슬라이더를 표시한다. 그 전에는 지금처럼 ROI 박스만 보인다.
- 층 순서는 원본 이미지 → 재구성 층(투명도 적용) → 기존 ROI 박스와 편집 손잡이다. 재구성 층은 클릭을 받지 않아 기존 ROI 선택·편집을 막지 않는다.
- 재구성 층에 그리는 순서:
  1. 원경 배경(`backdrop`)을 원본 전체에 그린다. `layers` 작업의 레이어는 지금처럼 원본 전체에 `order` 순서로 그린다.
  2. 바닥 타일 채우기(아래 2절)
  3. 오브젝트를 `plan.order` 오름차순으로, 같은 오브젝트 안에서는 자리의 아래쪽 y가 작은 것부터 그린다. 각 자리의 사각형에 맞춰 늘이거나 줄인다.
- 기준 이미지가 없는 에셋은 그 자리들에 점선 윤곽만 그리며, 윤곽은 투명도와 무관하게 보인다(PR #16 규칙 유지).
- 슬라이더는 라벨이 있는 native range 0~100%, 기본 50%이며 `aria-valuetext`로 현재 값을 알린다.
- 재구성은 서버 저장값이 아니라 화면의 미저장 draft(역할·자리·격자 칸 너비)를 따라 편집 즉시 다시 그린다. 타일 채우기는 칸 크기·타일 후보(역할이 `tile`인 에셋과 그 기준 이미지 ID)·원경 배경 이미지가 바뀔 때만 다시 계산하고, 자리만 바뀌면 오브젝트 층만 다시 그린다.
- 취소된 작업은 지금처럼 계획 검수 화면을 그리지 않으므로 재구성도 보이지 않는다.
- PR #16의 별도 "원본 비교" 패널(`SpriteSourceCompare.tsx`)과 그 E2E는 이 화면으로 대체되므로 제거한다. `rules.ts`의 `assetSourceRect`는 오브젝트 자리 목록을 다루도록 바꾸거나 새 순수 함수로 대체한다.

### 2. 바닥 타일 반복 채우기 (Frontend 순수 계산)

- 대상은 역할이 `tile`이고 기준 이미지가 있는 에셋이다. 칸 크기는 기존 `cellWidthOf` × 원본 너비이고, 높이는 isometric이면 그 절반(다이아몬드 격자), 아니면 같은 값(사각 격자)이다.
- 칸 선택: 원본의 칸 영역과 각 타일 이미지를 같은 칸 크기에서 비교한다. 다이아몬드 마스크와 타일 알파 128 이상인 점만 쓰고, 칸을 4×2 구역으로 나눈 평균 RGB의 거리가 가장 작은 타일을 고른다(시안과 같은 방식).
- 격자 위치: 원본과 생성 타일의 격자 기준점이 정해져 있지 않으므로, 칸 크기 안에서 8px 간격으로 기준점을 바꿔 보며 전체 거리가 가장 작은 위치를 쓴다.
- 원경 배경(`backdrop`)에 기준 이미지가 있으면 칸마다 배경도 후보로 넣는다. 배경이 가장 비슷한 칸은 타일을 놓지 않아 배경이 보이게 한다. 배경이 없으면 모든 칸에 타일을 놓는다.
- 오브젝트가 덮는 칸도 바닥 타일로 채우며 오브젝트가 그 위에 그려진다. 반복축 설정(`x`·`y`·`both`)과 관계없이 원본 전체를 채운다. 칸마다 독립적으로 고르므로 반복축 제한이 필요 없다.
- 픽셀을 읽어야 하므로 원본·타일 이미지를 `crossOrigin="anonymous"`로 불러온다. 로컬 dev CORS 정책은 이미지 응답에도 `Access-Control-Allow-Origin`을 붙이는 것을 확인했다(2026-10-16). Azure 운영 CORS에서도 같은지는 구현 때 확인한다. 픽셀을 읽지 못하면 재구성 층 대신 실패 이유를 표시하며, 빈 화면이나 한 칸 배치로 조용히 바꾸지 않는다.
- 계산 결과는 기준 이미지 ID 조합이 같으면 다시 계산하지 않는다.
- 선택 규칙·격자 좌표·기준점 탐색은 화면과 분리된 순수 함수로 두고, 픽셀 배열을 입력으로 받아 단위 테스트한다.

### 3. 오브젝트 여러 자리 (Backend + Frontend)

**도메인·저장**
- `SpriteAssetPlan`에 nullable `Placements`(원본 대비 0~1 `Bounds` 목록)를 추가한다. 재구성에 쓰는 자리 전체 목록이다. `SourceBounds`는 지금처럼 생성 기준 영역으로 남는다.
- 오브젝트 역할만 `Placements`를 가진다. 개수는 1~20개, 각 자리는 기존 `SourceBounds`와 같은 원본 내부·양수 크기 규칙을 따른다. 오브젝트가 아닌 역할에 값이 있으면 `SpritePlanInvalid`로 거부한다.
- `Placements`가 null인 오브젝트(기존 작업, 역할을 오브젝트로 바꾼 직후)는 `[SourceBounds]`로 취급한다. 서버 응답은 저장값을 그대로 돌려주고 Frontend reader가 이 기본값을 적용한다. `PlanJson`은 JSON 열이라 열 추가 migration은 필요 없다. 단, 필드가 없는 기존 JSON이 null로 읽히는지는 테스트로 확인한다.
- `Placements`는 `GenerationChanged`에 넣지 않는다. 현재 `ReplaceSpritePlan`은 계획이 조금만 달라져도 `SpriteAsset.UpdatePlan`에서 승인을 지우고 `Touch`로 해당 ZIP의 현재 표시를 내리며, 완료 작업을 검수 대기로 다시 연다. 저장 요청에서 바뀐 것이 `Placements`뿐이면 이 경로를 타지 않는다. 계획과 작업 revision만 올리고 이미지·승인·현재 ZIP·작업 상태·단계·`CompletedAt`은 그대로 둔다(완료 작업 포함). 이름·순서 등 다른 필드가 함께 바뀌면 기존 규칙을 따른다.
- 레코드의 목록 필드는 참조 비교가 되므로, 계획 비교·dirty 판정·변경 감지에서는 값으로 비교한다.

**API**
- 작업 조회 응답의 계획과 `PUT /api/jobs/{id}/sprites/plan` 요청 본문에 nullable `placements`를 추가한다. 이름과 직렬화 방식은 기존 sprite DTO 규칙을 따른다.
- HTTP 계약 변경이므로 양쪽 스택을 검증하고 [api-breaking-change-detector](../../../.agents/skills/api-breaking-change-detector/SKILL.md)로 검토한다. Frontend `readSpriteJob`은 누락만 null로 호환하고 형식이 잘못되면 지금처럼 계약 오류로 거부한다.

**계획 검수 편집**
- 생성 기준 상자와 자리 상자는 따로 둔다(사용자 결정). 오브젝트는 생성 기준 상자 1개(`SourceBounds`)와 자리 상자 여러 개(`Placements`)를 함께 그리며, 두 종류는 모양과 접근 가능한 이름으로 구분한다.
  - 생성 기준 상자는 지금과 같다. 옮기거나 크기를 바꾸면 `GenerationChanged`에 걸려 재생성된다. 지울 수 없다.
  - 자리 상자는 옮기거나 크기를 바꿔도 재생성되지 않는다. 처음에는 생성 기준 상자와 같은 위치에 겹쳐 보일 수 있다.
- 자리 추가, 삭제(최소 1개 유지), 이동·크기 조절을 제공한다. 이동·크기 조절은 기존 `useSpriteRoiEditor`의 선택·손잡이·키보드·취소 규칙을 그대로 따른다.
- `Placements`가 null인 오브젝트는 화면에서 `[SourceBounds]`의 복사본을 자리 1개로 보여 준다. 사용자가 자리를 처음 편집하면 그 복사본이 draft의 `placements`가 된다. 생성 기준 상자를 옮겨도 이 복사본은 따라 움직이지 않는다.
- V5 프롬프트의 "`sourceBounds`는 자리 중 하나" 지시는 AI 응답의 품질 기준일 뿐 서버 검증 규칙이 아니다. 두 값은 저장 후 각자 편집된다.
- 자리 편집은 기존 계획 저장 흐름(`expectedRevision`, 409 처리, 미저장 draft 보존)으로만 서버에 보낸다. 드래그만으로는 요청을 만들지 않는다.
- 역할을 오브젝트에서 다른 역할로 바꾸면 draft의 `placements`를 비운다.

### 4. 분석 프롬프트 V5 (Backend)

- `AnalyzeSpritesV4`를 바탕으로 `AnalyzeSpritesV5`를 추가한다.
  - 타일 설명에서 벽을 빼고 "바닥처럼 넓게 깔리는 칸(땅·물·도로·인도)"으로 한정한다.
  - 서 있는 벽·담장·건물 외벽·지붕·차양은 오브젝트로 분류하라고 명시한다.
  - 오브젝트는 원본에 나오는 모든 위치를 `placements`(최대 20개)로 돌려주고, `sourceBounds`는 그중 가장 잘 보이는 하나로 고르게 한다.
  - 긴 벽·담장처럼 출력 상한(`SpriteRules.AssetOutput`의 1024px)을 넘을 만큼 큰 구조물은 반복되는 구간 하나를 오브젝트로 잡고, 나머지 구간을 `placements`로 나열하게 한다. 상한을 넘는 계획은 지금처럼 검증 실패와 재시도로 처리한다.
- 스키마: 에셋 항목에 `placements`를 추가한다. OpenAI 호환을 위해 V4의 `grid`처럼 `anyOf`로 null을 허용한다.
- migration은 V4 개정 방식을 따른다. V4 시드가 활성이고 수정되지 않았을 때만 그것을 비활성화하고 V5를 `MAX(Version)+1`로 켠다. 그렇지 않으면(운영자 버전이 활성이면) 아무것도 바꾸지 않는다. Down은 V5 행을 지우고, Up에서 비활성화한 경우에만 V4를 다시 켠다.
- 따라서 V5가 켜지지 않은 환경에서는 `placements`가 없는 응답이 계속 들어온다. `SpritePlanParser`는 `placements`가 있는 응답과 없는 응답을 모두 받고, 있으면 3절과 같은 규칙으로 검증한다.
- `FakeLlmProvider`의 타일 분석은 자리가 2개 이상인 오브젝트를 하나 이상 돌려준다.

## 사용자가 정한 것

- 목적: 원본 구도를 생성 에셋으로 얼마나 똑같이 만들 수 있는지 판단한다.
- 제작 계획 검수가 끝나면 계획 검수 화면의 원본 이미지 위에 투명도로 겹친다.
- 타일은 한 칸이 아니라 반복해서 원본과 최대한 비슷하게 채운다.
- 벽과 지붕은 타일이 아니라 오브젝트로 따로 배치한다.
- 오브젝트는 원본에 나오는 모든 자리에 놓는다.
- 자리는 AI 분석이 찾고 계획 검수에서 사람이 고친다.
- 오브젝트의 생성 기준 상자와 자리 상자는 따로 둔다. 자리 상자 편집은 재생성을 일으키지 않는다.

## 설계자가 정한 것

다음은 사용자가 확인하지 않은 판단이며 검토 때 바꿀 수 있다.

- 별도 원본 비교 패널을 없애고 계획 검수 화면으로 옮긴다.
- 타일 선택은 4×2 구역 평균색 거리, 격자 기준점은 8px 간격 탐색이다(시안 방식).
- 오브젝트는 자리마다 사각형에 맞춰 늘이거나 줄인다. 원본과 겹쳐 비교하는 목적에 맞추기 위해서다.
- 자리 편집은 재생성·승인 무효화를 일으키지 않는다.
- 자리는 오브젝트당 최대 20개다(3D `placements`와 같은 상한).
- 기본 투명도는 50%다.
- 원경 배경이 있으면 칸마다 배경도 후보에 넣어, 배경이 더 비슷한 칸은 비워 둔다.
- 재구성은 미저장 draft를 따라 즉시 다시 그린다.
- 자리만 바꾼 저장은 revision만 올리고 승인·현재 ZIP·작업 상태·단계를 유지한다.
- V5 migration은 V4처럼 운영자 버전이 활성이면 켜지지 않는다. 파서는 `placements` 유무를 모두 받는다.
- 출력 상한을 넘는 긴 벽은 구간 오브젝트 하나와 여러 자리로 나누도록 프롬프트에서 지시한다.
- 취소된 작업에서는 재구성을 보여 주지 않는다(계획 검수 화면을 그리지 않는 현재 규칙 유지).
- 구현 순서는 1·2절(현재 ROI 한 자리 기준으로 먼저 동작) → 3절 → 4절이다. 1·2절은 Frontend만으로 먼저 전달할 수 있다.

## 구현자에게 맡기는 것

- 자리 추가·삭제 버튼의 위치와 문구는 기존 계획 검수 패턴 안에서 정한다.
- 재구성 계산이 화면을 멈추게 하면 Web Worker나 분할 계산을 쓴다. 계산 시간은 실제 작업 크기(원본 1536×1024, 타일 8종)로 측정해 기록한다.
- V5 프롬프트의 정확한 문장은 정하되, 위 규칙과 V4의 기존 지시를 유지한다.

## 제약

- 작업 상태의 정본은 SQL Server다. 재구성 결과와 타일 선택은 저장하지 않고 화면에서 매번 계산한다.
- 실제 AI 호출(V5 품질 확인 포함), 유료 smoke, Docker 재배포, PR 병합은 사용자가 승인한 범위에서만 한다.
- 계층 경계: 픽셀 계산 순수 함수는 `src/domain/sprites/`, 이미지 로딩·canvas는 `features/screens/sprites/`, URL은 `app/queries/media.ts`를 거친다.

## 검증

- **Backend**: `Placements` 검증(역할·개수·범위), null 기본 처리와 기존 JSON 호환, 자리만 바꾼 저장에서 이미지·승인·현재 ZIP·작업 상태·단계·`CompletedAt` 유지(완료 작업 포함)와 다른 필드가 함께 바뀔 때의 기존 동작, 계획 저장 API 요청·응답, `SpritePlanParser`의 `placements` 유무 양쪽 수용, V5 migration Up·Down·운영자 버전 활성 시 무변경(격리 SQL), `SeedPromptVariableTests`. 이후 Backend 전체 회귀(유료 smoke 제외)를 돌린다.
