# 2D 배경 스프라이트·애니메이션 제작 설계

작성일: 2026-10-06

상태: 대화에서 합의한 범위의 설계안. 문서 검토 후 구현 계획을 작성한다. 아래 신규 필드·API·단계는 현재 구현을 설명하지 않는다.

## 1. 목적과 합의한 범위

Noxtend에 이미지 기반 2D 배경 제작 흐름을 추가한다. 사용자는 배경 이미지를 입력하고 게임에서 사용할 배경 레이어 또는 반복 타일을 만든다. 움직이는 환경 요소는 프레임 애니메이션으로 제작하고, 결과를 검수한 뒤 PNG·스프라이트 시트·JSON을 내려받는다.

사용자가 정한 사항:

- 메뉴는 홈, 3D(캐릭터·배경·오브젝트), 2D(캐릭터·배경·오브젝트)로 구성한다.
- 1차 구현은 2D 배경이다. 2D 캐릭터·오브젝트는 미구현 항목으로 표시한다.
- 횡스크롤·탑다운·아이소메트릭 시점을 작업마다 선택한다.
- 배경 레이어와 반복 타일을 작업마다 선택한다.
- 이미지 입력으로 먼저 완성하고, 이후 텍스트로 기준 이미지를 만드는 입력 단계를 추가한다.
- 애니메이션은 프레임별로 생성하고 개별 검수·재생성을 지원한다.
- 기존 이미지 공급자·작업 실행·큐·저장소를 재사용한다.

추가 설계 결정:

- 한 작업은 레이어 또는 타일 중 한 결과 유형을 갖는다. 같은 원본으로 다른 유형의 작업을 시작할 수 있다.
- 화풍은 원본을 유지한다. 스프라이트라는 이유로 픽셀 아트로 강제 변환하지 않는다.
- 1차 애니메이션은 물결·불·깃발·식물 흔들림 등 배경 요소의 반복 동작이다. 사용자가 분석된 대상별로 정적/애니메이션을 선택하고 동작 설명을 수정한다.
- 기준 이미지 승인 후 애니메이션을 생성해, 사용할 수 없는 기준 이미지로 후속 호출이 진행되는 것을 막는다.
- 메뉴의 3D 오브젝트는 현재의 준비 중 상태를 유지한다.

성공은 파일을 생성했다는 사실과 시각적 품질을 구분해 판단한다. 레이어 합성·타일 반복·애니메이션 재생에서 사람이 사용할 수 있다고 승인한 결과가 있고, 해당 승인 버전의 파일과 설정을 일관되게 내보낼 수 있어야 한다.

## 3. 메뉴와 주소

```text
홈
3D
  캐릭터
  배경
  오브젝트 · 준비 중
2D
  캐릭터 · 준비 중
  배경
  오브젝트 · 준비 중
관리자 · 하단 영역
```

- 데스크톱에서는 3D·2D를 클릭 목적지가 없는 그룹 제목으로 표시한다. 그룹을 접는 별도 상태는 만들지 않는다.
- 사이드바를 접어도 두 그룹을 구분하고, 툴팁·접근 가능한 이름에 `3D 배경`, `2D 배경`처럼 전체 이름을 사용한다.
- 기존 `/character`, `/background`, `/object`와 작업 ID 주소를 유지한다.
- 새 주소는 `/2d/background`, `/2d/background/:jobId`, `/2d/character`, `/2d/object`다. 미구현 주소는 기존 준비 중 화면의 표현을 재사용한다.
- 작업 상세 주소에서 상위 제작 메뉴도 활성 상태가 된다.
- 720px 이하에서는 하단 탐색을 홈·3D·2D·관리자 네 항목으로 구성한다. 3D·2D는 접근 가능한 메뉴를 열고 하위 제작 항목을 고른다. 현재 페이지가 속한 그룹과 대상 이름을 표시한다.
- 홈의 실행 중·최근 작업 목록은 2D/3D와 카테고리를 함께 표시하고 각 작업의 제작 화면으로 연결한다.
- 라우트 상수·메뉴 정의·지연 import는 현재의 `paths.ts`, `navItems.ts`, `prefetch.ts` 경계를 유지한다.

## 4. 입력과 설정

이미지 입력은 기존 업로드의 PNG·JPEG·WebP, 12 MiB 상한을 유지한다. 서버에서 디코딩 가능 여부와 실제 픽셀 크기도 검사한다. 2D 입력의 디코딩 상한은 16,777,216픽셀로 정하고 초과 시 명확히 거부한다.

기존 결과에서 진입할 때는 서버가 결과 이미지의 저장소 참조를 확인하고 2D 입력으로 연결한다. 사용자가 Blob 키나 외부 URL을 직접 입력하지 않는다. 원본 작업 삭제가 2D 작업의 입력을 제거하지 않도록 새 업로드 이미지로 복사하여 독립된 저장소 키를 갖게 한다.

작업 설정:

| 설정 | 설계 값 |
| --- | --- |
| 시점 | `sideView`, `topDown`, `isometric`; 필수 선택 |
| 결과 유형 | `layers`, `tiles`; 필수 선택 |
| 공급자·모델 | 분석용 텍스트 모델과 생성용 이미지 모델을 각각 선택 |
| 레이어 캔버스 | 원본 비율 유지, 긴 변 최대 1024px; 원본을 확대하지 않음 |
| 타일 크기 | 너비 64·128·256px, 기본 128px |
| 타일 배치 | 횡스크롤·탑다운은 정사각 격자; 아이소메트릭은 너비:높이 2:1 다이아몬드 프리셋 |
| 반복 방향 | 가로·세로·양쪽; 기본 양쪽, 다이아몬드에서는 격자의 두 축 기준 |
| 애니메이션 | 대상별 opt-in; 기본 정적 |
| 프레임 수 | 애니메이션 4·8프레임, 기본 8; 정적 결과는 1프레임 |
| 재생 속도 | 기본 8 FPS, 1~30 FPS |
| 제작 대상 수 | 작업당 1~12개 |
| 생성 계획 상한 | 승인하는 생성 묶음당 기준 이미지 포함 최대 64프레임 |

이 상한은 자원·호출 수를 제한하기 위한 초기 설계값이며, 측정된 품질이나 처리량을 주장하는 수치가 아니다. 계획 상한을 초과하면 대상을 조정하도록 안내하고 일부를 몰래 누락하지 않는다.

레이어 캔버스는 비율을 유지해 정수 픽셀로 반올림한다. 생성 공급자의 해상도와 내보내기 해상도는 구분한다. 생성 크기는 공급자가 지원하는 규격으로 요청하고, 최종 캔버스에는 같은 좌표 변환으로 비율을 유지해 배치한다. 공급자가 지원하지 않는 형상은 접수·계획 승인 전에 거부하며 숨은 잘라내기나 비율 왜곡을 하지 않는다.

원본 영역은 정규화된 `x, y, w, h`로 받고, 각 값은 유한하며 영역이 원본 안에 있어야 한다. 너비·높이가 0 이하이거나 범위를 벗어나면 거부한다. 레이어의 기본 앵커는 최종 캔버스 왼쪽 위 `(0, 0)`, 타일은 셀 중심이다. 앵커는 최종 프레임의 픽셀 좌표로 저장한다.

분석 결과는 추천이다. 원본에서 이미 쓰는 시점과 선택한 시점이 다르면 새 시점으로 재구성하는 작업임을 알린다. 시점 선택은 좌표 변환만으로 완성되었다고 처리하지 않는다.

## 5. 제작 흐름과 검수

```text
입력·설정
  → 제작 대상 분석
  → 제작 계획 검수
  → 기준 이미지 생성
  → 기준 이미지 검수
  → 애니메이션 프레임 생성 · 정적 대상은 생략
  → 애니메이션 검수
  → 승인 결과 패키징
  → 결과 다운로드
```

### 제작 계획 검수

- 레이어 모드는 전경·중경·후경에 해당하는 후보, 순서, 포함 영역을 제안한다. 사용자는 대상 추가·삭제·이름·영역·순서를 수정한다.
- 타일 모드는 원본에서 지면·벽·물 등 반복할 영역을 제안한다. 원본 내 추출 영역과 최종 반복 타일은 다른 정보로 저장한다.
- 각 대상에 정적/애니메이션, 동작 설명, 프레임 수를 지정한다. 자유 설명은 500자 이내이며 프롬프트 변수 구문으로 재해석하지 않는다.
- 승인 전에 대상별 생성 수와 모델을 표시한다. 단가가 없으면 비용을 미확인으로 표시한다.
- 승인한 계획을 revision과 함께 고정하고 기준 이미지 생성 공정을 만든다.

### 기준 이미지 검수

- 레이어는 동일한 캔버스로 합성해 원본 구도·가림·빠진 영역을 확인한다. 앞 레이어를 제거했을 때 나타나는 뒷배경도 검수한다. 단순 사각형 crop을 레이어 분리 완료로 간주하지 않는다.
- 타일은 직사각 또는 다이아몬드 격자에 최소 3×3 반복 배치해 경계를 확인한다.
- 기준 이미지가 부적합하면 대상별로 재생성한다. 다른 대상의 승인·이미지를 보존한다.
- 정적 대상은 이 검수에서 최종 이미지 승인이 끝난다. 애니메이션 대상은 승인한 기준 이미지를 프레임 0으로 고정한다.
- 선택한 애니메이션 대상들의 기준 이미지 승인이 완료되면 해당 묶음의 나머지 프레임을 생성한다.

### 애니메이션 검수

- 프레임 `i`는 주기의 `i / frameCount` 위치로 요청한다. 마지막 프레임을 첫 프레임의 복사본으로 강제하지 않는다.
- 모든 프레임에 같은 원본·승인 기준 이미지·시점·화풍·캔버스·좌표·앵커를 적용한다. 직전 프레임만 이어 참조해 형태 오차가 누적되는 방식은 사용하지 않는다.
- 프레임 목록과 재생·일시정지·프레임 이동·FPS 조절을 제공한다. 레이어 합성 또는 타일 반복 상태에서도 재생한다.
- 사용자는 형태·색상·위치의 흔들림과 마지막→첫 프레임 전환을 보고 대상 단위로 승인한다. 부적합 프레임만 새로 생성할 수 있다.
- 대상의 프레임 수·동작·영역·기준 이미지가 바뀌면 해당 대상의 애니메이션 승인을 취소하고 후속 프레임을 새 계획으로 생성한다.
- 작업 공통 시점·결과 유형·캔버스 크기는 접수 후 고정한다. 이를 바꾸려면 같은 원본으로 새 작업을 만든다.
- FPS·표시 이름·레이어 순서만 바뀌면 AI를 다시 호출하지 않고 검수와 패키지만 갱신한다.

## 6. 서버 구조와 도메인 경계

새 심볼은 구현 계획에서 파일 배치를 정하되 다음 책임을 갖는다.

| 책임 | 설계 |
| --- | --- |
| 작업 분류 | `PipelineJob.ProductionMode`: `ThreeD`, `TwoD`; 카테고리는 기존 `AssetCategory.Background` |
| 2D 작업 상태 | 작업이 소유하는 `SpritePipelineState`; 설정·계획·검수 단계·대상·프레임·승인 snapshot |
| 분석 | `AnalyzeSprites` 공정; 별도 2D 분석 스키마와 응답 검증 |
| 기준/프레임 생성 | `GenerateSprite` 공정; 대상 ID·프레임 번호·계획 revision·고정 기준 이미지 ID로 구분 |
| 패키징 | `PackSprites` 공정; 승인 snapshot을 입력으로 사용하며 AI 호출 없음 |
| 실행 | 기존 `TaskWorker`·`TaskExecution`·`JobOrchestrator`·Redis Streams 등록 경로 확장 |
| 이미지 생성 | 기존 `IImageProvider`·Factory·기록 데코레이터·`RateLimitGate` 재사용 |
| 이미지 처리 | Infrastructure의 SkiaSharp 처리, Domain Port를 통해 호출; 캔버스 정규화·PNG 알파 보존·시트 합성 |
| ZIP | .NET `System.IO.Compression` 사용, 서버 생성 파일명과 저장소 키 |

`PipelineJob`의 후속 공정 계획·실행 준비·상태 집계는 제작 모드별 규칙을 호출한다. 큐·공통 실행기에서 카테고리나 프레임 검수 조건을 다시 판단하지 않는다. 기존 3D 규칙과 새 2D 규칙에 같은 검수 필드를 혼용하지 않는다.

`GenerateSprite`의 기준 이미지 공정은 분석과 계획 승인 뒤 시작한다. 프레임 1 이후는 승인된 프레임 0 공정에 의존하고 참조 이미지 ID를 고정한다. `PackSprites`는 승인한 이미지 ID 목록을 입력으로 갖는다. 여러 부모를 하나의 `DependsOnTaskId`로 가장하지 않는다.

원본 모드와 다른 API(2D 작업에 3D 생성, 3D 작업에 sprite 검수 등)는 실패시킨다. 제작 모드는 생성 이후 바꾸지 않고 다른 모드의 작업을 새로 만든다.

## 7. 상태·재시도·동시성

공통 JobStatus를 유지하고 2D 단계는 별도로 표현한다. 2D 단계는 분석, 계획 검수, 기준 생성, 기준 검수, 프레임 생성, 프레임 검수, 내보내기 대기, 패키징, 완료다. 정적 대상만 있으면 프레임 생성·검수를 생략한다. 단계는 서버 상태의 진행 요약이며, 실제 실행 준비는 대상·프레임의 의존과 승인 상태로 판정한다.

| 상태 | 2D에서의 의미 |
| --- | --- |
| `pending`, `running` | 실제 실행 대기·실행 중인 공정 존재 |
| `pendingReview` | 계획·기준 이미지·애니메이션 검수 또는 내보낼 대상 선택 대기; 종료 상태 아님 |
| `succeeded` | 요청 대상 전부가 승인되고 해당 snapshot의 패키지가 저장됨 |
| `partiallySucceeded` | 승인된 일부 대상만 패키징해 현재 제작을 마쳤거나, 검수 가능한 결과를 남기고 패키징 실패 |
| `failed` | 분석 실패 또는 생성 종료 후 사용 가능한 대상이 없음 |
| `canceled` | 취소된 작업; 이후 AI 결과를 현재 결과로 반영하지 않음 |

- 작업 상태와 별도로 대상별 생성·검수 상태를 반환한다. 일부 대상 실패가 다른 대상의 결과를 지우지 않는다.
- 모든 실행이 끝났어도 검수하지 않은 결과는 자동 승인하거나 완료 패키지로 내보내지 않는다. 사용 가능한 미승인 결과가 있으면 검수를 계속할 수 있다.
- 상태 집계는 취소 → 현재 공정 실행/대기 → 필요한 검수/내보내기 선택 → 패키징 종료 결과 순서다. 공정 일부가 실패해도 검수 가능한 결과가 남으면 `pendingReview`에서 실패 표시와 복구 행동을 함께 제공한다. 모든 생성이 실패해 검수할 결과가 없으면 `failed`다.
- 내보내기 대기에서는 추가 승인 버튼 대신 패키지 생성 행동을 표시한다. 일부 대상만 내보내면 남은 요청 대상은 manifest와 UI에서 제외된 대상으로 명시하고 작업은 부분 성공으로 끝낸다. 이후 추가 제작은 명시적 재개 요청으로 시작한다.
- 실패한 프레임의 재시도와 성공했지만 품질이 나쁜 프레임의 재생성은 구분한다. 재생성은 새 공정·결과 ID를 갖는다.
- 재시도·재생성·패키지 재생성을 접수할 때 필요한 종료 작업을 명시적으로 재개한다. 공통 실행기의 종료 작업 skip 규칙을 우회하지 않는다. 취소 작업은 재개하지 않고 새 작업으로 이어받는다.
- 변경·승인 요청은 `expectedRevision`을 받는다. 충돌은 409로 알리고 최신 상태를 다시 읽도록 한다.
- 실행 중인 대상의 생성 입력 변경과 같은 슬롯의 새 재생성 요청은 409로 거부한다. 같은 `requestId`의 재전송은 기존 접수 결과를 반환한다. 완료한 다른 대상의 검수·내보내기는 유지한다.
- 각 프레임 슬롯은 현재 실행 공정 ID와 결과 ID를 갖는다. 결과 반영 시 계획 revision·현재 공정 ID·취소 상태를 모두 확인해 늦은 결과가 새 결과를 덮지 못하게 한다.
- 한 프레임을 바꾸면 그 대상을 포함한 애니메이션 승인·최신 패키지 자격만 취소한다. 이미 내려받을 수 있는 과거 패키지는 고정 snapshot으로 보존한다.
- 신규 생성·승인·재생성 요청은 `requestId`로 중복을 식별하고 같은 요청의 공정을 반환한다. 같은 ID에 다른 본문을 보내면 충돌이다. 계획 fan-out과 패키징도 중복 실행으로 새 결과를 추가하지 않는다.
- 요청 ID와 본문 fingerprint·해당 공정 ID를 SQL에 보존한다. 동일 요청 조회는 revision 검사보다 먼저 하므로 이미 성공한 승인을 재전송해도 같은 접수 결과를 반환한다. 새 요청만 현재 revision과 상태 전이를 검증한다.
- 공급자 transient 오류·429는 기존 제한·backoff·시도 상한을 따른다. 인증·크레딧·미지원 설정·디코딩/자원 상한 오류를 무조건 재호출하지 않는다.
- 외부 호출 성공과 SQL 저장 사이의 장애가 유료 재호출을 완전히 배제하지는 않는다. 중복 메시지 처리와 공급자 과금의 exactly-once를 같은 보장으로 설명하지 않는다.

## 8. 저장과 이전 데이터 호환

설계 저장 모델:

| 저장 대상 | 내용 |
| --- | --- |
| `Jobs` 추가 필드 | 제작 모드, 2D 설정, 2D 검수 단계·revision |
| `Tasks` 추가 필드 | sprite 대상 ID·프레임 번호·계획 revision·고정 참조·요청 ID |
| `SpriteAssets` | 레이어/타일 대상, 이름·순서·영역·앵커·애니메이션 설정·계획 revision |
| `SpriteFrames` | 대상·프레임 번호별 슬롯, 현재 공정·현재 이미지 ID |
| `SpriteImages` | 생성 결과 이력, 공정·기준 이미지·Blob·픽셀 크기·형식·계획 revision |
| `SpriteExports` | 승인 snapshot·manifest·패키지 Blob·패키징 공정 ID |
| `SpriteRequests` | 생성·승인·재생성·내보내기의 요청 ID·종류·본문 fingerprint·작업·공정 ID와 접수 결과 |

계획 revision은 동작·시점·영역·크기 등 생성 입력이 바뀔 때 갱신한다. 검수 revision은 표시 설정·승인·현재 프레임 변경에도 갱신한다. 결과 검수·패키징은 검수 revision과 선택 이미지 ID 목록을 함께 확인한다.

행의 관계·고유성·rowversion·삭제 정책은 EF 설정과 SQL 제약으로 검증한다. 슬롯은 대상·프레임 번호가 유일하고, 패키지 입력은 결과 이미지 ID 목록으로 고정한다. 저장 JSON은 스키마 버전을 갖고 유효성 검사를 거친다.

`SpriteRequests`의 요청 ID는 유일하며 상태 변경·공정 계획과 같은 SQL 트랜잭션에 저장한다. 본문 fingerprint는 검증·정규화한 입력의 SHA-256으로 만든다. 중복 요청 경쟁은 고유 제약·rowversion을 통해 처리하고, 새 유료 공정을 계획하기 전에 기존 접수 결과를 반환한다.

후속 migration으로 기존 `Jobs`의 제작 모드를 `ThreeD`로 채운다. 메시 공급자가 없는 기존 작업도 기존 스튜디오에서 만든 작업이므로 3D 그룹에 남는다. 메시 유무로 제작 모드를 추론하지 않는다. 2D 필드·관계는 기존 행에서 비어 있어야 하며, 기존 3D JSON·API를 계속 읽을 수 있어야 한다.

Blob은 성공 확정 전에 저장하고 SQL에는 서버가 생성한 키를 기록한다. 패키징 실패로 현재 프레임이 삭제되지 않는다. 작업 삭제 때 2D 이미지·패키지도 기존 삭제 절차에 포함한다. 공유 결과를 참조하는 입력은 독립 Blob 복사로 보존한다.

## 9. API와 Frontend 연결

공통 JSON 봉투·오류 매핑·파일 응답 규칙을 유지한다. 아래 경로는 신규 계약 설계다.

| API | 역할 |
| --- | --- |
| `POST /api/jobs/sprites` | 업로드 이미지 또는 기존 결과 이미지에서 2D 배경 작업 접수; `requestId`, 시점·결과 유형·모델 선택 |
| `GET /api/jobs/{id}` | 기존 상세 응답에 제작 모드와 nullable `sprite` 상세 추가 |
| `GET /api/jobs` | 기존 목록·total 의미 유지, 제작 모드 필터와 요약 필드 추가 |
| `PUT /api/jobs/{id}/sprites/plan` | 대상·영역·정적/애니메이션 계획 수정; revision 확인 |
| `POST /api/jobs/{id}/sprites/plan/approve` | 계획 snapshot 승인·기준 이미지 생성 |
| `POST /api/jobs/{id}/sprites/base/approve` | 선택 대상의 기준 이미지 승인·후속 프레임 생성 |
| `POST /api/jobs/{id}/sprites/assets/{assetId}/frames/{index}/regenerate` | 프레임별 재생성; 기준 이미지 교체는 후속 프레임 재계획 |
| `POST /api/jobs/{id}/sprites/assets/{assetId}/approve` | 애니메이션 검수 snapshot 승인 |
| `POST /api/jobs/{id}/sprites/exports` | 승인 대상 명시 선택·패키징 접수 |
| `GET /api/jobs/{id}/sprites/images/{imageId}` | 저장 결과 PNG |
| `GET /api/jobs/{id}/sprites/exports/{exportId}` | 고정 snapshot ZIP 다운로드 |

실패한 sprite 공정의 재시도·작업 취소·삭제는 기존 공통 경로를 확장한다. 기존 `POST /api/jobs`는 3D 계약을 유지한다. 추가 응답 필드는 서버와 Frontend 파서를 함께 수정하고, 기존 작업의 제작 모드 누락 읽기는 `threeD`로 처리한다.

원본 선택은 `uploadId` 또는 `sourceJobId`·`sourceGeneratedImageId` 쌍 중 정확히 하나다. 서버에서 원본 결과가 지정한 원본 작업에 속하는지 확인한다. 파일 URL·Blob 키를 받지 않는다. 이후 sprite 검수·이미지 조회·패키징 API는 대상·결과가 주소의 2D 작업에 속하는지 확인한다. 지원하지 않는 2D 카테고리·유형·시점·범위·프레임 번호를 거부한다.

내보내기 요청은 `expectedRevision`, `requestId`, 1개 이상의 승인 대상 ID를 받는다. 서버가 대상의 현재 승인 snapshot을 확인하고 이미지 ID 목록을 고정한다. 클라이언트가 보낸 임의 이미지 목록으로 패키지를 구성하지 않는다.

Frontend는 기존 `domain → infra → app/queries → features → routes` 경계를 유지한다. 제작 모드·작업 ID·유형·필터를 실제 요청에 맞춰 query key에 반영한다. 새 화면에서 직접 fetch·폴링 상태 머신을 만들지 않는다. 서버 상세를 정본으로 사용하고 편집 draft와 재생 위치만 로컬에 둔다.

## 10. 생성 계약·이미지 검증

2D 분석·이미지 생성 프롬프트는 기존 3D 프롬프트와 별도 operation으로 등록한다. 분석은 선택 시점·유형과 제작 대상의 구조화 스키마를 사용한다. 대상 ID·이름·영역·순서·반복 방향·동작을 검증하고 미확인 대상을 조용히 추가하지 않는다.

생성 호출에는 원본과 승인 기준 이미지의 역할을 구분해 전달한다. 프레임 번호·주기 위치·고정해야 할 요소를 명시한다. `ViewDirection.Front` 같은 3D 의미를 프레임 번호 대신 사용하지 않는다.

현재 어댑터의 정사각 크기·투명 배경 요청을 확인하고, 2D 요청에 필요한 크기·배경 옵션을 명시적으로 전달하도록 확장한다. 기존 3D 요청의 기본값은 유지한다. 모델별 지원 여부는 공급자 이름 하나로 판단하지 않는다.

- 레이어 전경·중경과 다이아몬드 타일은 투명 배경이 필요하다. 해당 요청을 지원하는 것으로 확인된 모델만 선택하도록 한다. 최초 지원은 OpenAI GPT Image의 문서화된 PNG 투명 배경 요청 경로를 사용한다.
- Google 등 다른 모델의 PNG 반환을 투명 배경 지원 증거로 사용하지 않는다. 투명 출력이 필요 없는 직사각 타일·후경은 해당 모델의 크기 지원을 검증한 후 사용할 수 있다.
- PNG 헤더·실제 디코딩·픽셀/바이트 상한·캔버스 크기·비어 있지 않은 콘텐츠를 검증한다. 투명 대상은 실제 알파 데이터를 확인하고, 흰 배경이나 체크무늬를 투명으로 간주하지 않는다.
- 모든 프레임은 같은 캔버스·앵커·좌표 변환을 쓴다. 프레임마다 바운딩 박스에 맞춰 자동 확대·재중앙 정렬하지 않는다.
- 최종 PNG의 알파를 보존한다. 기존의 배경색을 채우는 평가용 정규화를 그대로 사용하지 않는다.
- 형태 일관성·가려진 부분의 복원·반복 경계·루프 자연스러움은 사람 검수 대상이다. 파일 검증이나 Fake 통과로 품질을 승인하지 않는다.

공식 안내도 생성 간 시각적 일관성과 정확한 배치에 한계가 있음을 설명한다. 프레임별 생성은 검수·수정 범위를 줄이는 설계이며, 모델 품질을 보장하는 기능이 아니다. [OpenAI 이미지 생성·제약](https://developers.openai.com/api/docs/guides/image-generation)

- [OpenAI 이미지 프롬프트·투명 배경 안내](https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)
- [Google 이미지 생성·참조 이미지 안내](https://ai.google.dev/gemini-api/docs/image-generation)

실행 기록에는 작업·공정·대상·프레임·기준 이미지 ID·프롬프트 버전·공급자·모델·사용량을 연결한다. 이미지 바이트와 키를 호출 내역·로그에 추가하지 않는다. 유료 모델 품질 평가는 [기존 평가 절차](../../xHuman/prompt-evaluation.md)의 승인·예산 범위에서만 수행한다.

## 11. 내보내기 계약

ZIP은 서버가 만든 안전한 파일명을 사용하고 다음을 포함한다.

```text
manifest.json
layers/asset-{id}.png                 # 레이어 모드의 승인 기준 이미지
tiles/asset-{id}.png                  # 타일 모드의 승인 기준 이미지
frames/asset-{id}/frame-000.png       # 해당 대상의 승인 프레임
sheets/asset-{id}-000.png             # 대상별 시트; 필요하면 여러 페이지
```

실제 패키지에는 선택한 결과 유형·대상에 해당하는 파일만 포함한다. 정적 대상도 1프레임으로 표현하고, 애니메이션은 지정한 프레임 전부가 있어야 포함할 수 있다.

manifest의 필수 정보:

- `schemaVersion: 1`, 작업·export ID, 제작 모드, 시점, 유형, 검수 revision
- 포함한 대상 ID와 원래 요청에서 제외된 대상 ID 목록
- 원본 픽셀 크기와 최종 캔버스 크기, 좌표 원점(왼쪽 위), 픽셀 단위
- 대상 ID·이름·레이어 순서 또는 타일 크기·격자 형태·반복 축
- 프레임 크기·고정 앵커, 기준 이미지 ID와 순서가 명시된 프레임 이미지 ID
- 상대 PNG 경로, 시트 페이지·프레임 rectangle, FPS, loop 여부

레이어 PNG는 모두 같은 캔버스에 놓고 manifest의 순서로 합성한다. 타일 PNG는 격자 셀 크기이며, 다이아몬드 타일의 빈 모서리는 알파로 보존한다. 모든 rectangle은 패딩을 제외한 실제 프레임 영역을 가리킨다.

시트는 프레임을 회전·trim하지 않고 같은 셀로 행 우선 배치한다. 프레임 주변 2px의 가장자리 확장 패딩을 두고 rect 좌표에는 이를 제외한다. 한 페이지는 최대 4096×4096px이며 페이지를 나눠 순서를 유지한다. 한 번에 한 페이지·한 입력 프레임만 처리하고 패키지는 스트리밍으로 구성한다. 패키지 상한은 256 MiB이며 초과 시 명시적으로 실패시킨다.

승인·패키징 사이에 설정이나 프레임이 바뀌어도 패키지 입력 snapshot을 섞지 않는다. 과거 패키지는 당시 파일과 manifest를 계속 내려준다. 승인된 일부 대상만 내보낼 때 선택 목록을 표시하고, 제외된 요청 대상이 있으면 전체 작업 성공으로 표시하지 않는다.

패키징 도중 새 revision이 생기면 완성한 과거 snapshot을 이력으로 보존할 수 있지만, 이를 최신 패키지나 현재 작업의 성공으로 확정하지 않는다. 취소 이후에는 새 패키지를 공개하지 않는다. 패키징 재시도는 같은 고정 입력을 사용하며 이미지 AI를 다시 호출하지 않는다.

이 JSON은 Noxtend의 명시적 내보내기 계약이다. PNG·좌표·재생 정보 제공과 특정 게임 엔진의 자동 import 지원은 구분한다.

## 12. 구현 순서와 검증 기준

하나의 설계 안에서 다음 순서로 구현한다. 세부 파일·테스트·커밋 단계는 후속 구현 계획에서 작성한다.

## 13. 후속 텍스트 입력

텍스트 입력은 `설명 → 기준 이미지 생성 → 기존 이미지 입력 접수`로 연결한다. 생성된 기준 이미지를 같은 업로드 저장 계약에 넣고, 이 문서의 설정·분석·프레임·검수·내보내기 경로를 재사용한다.

텍스트 단계의 입력 검증·프롬프트·비용·실패 처리는 그 단계에 둔다. 입력 경로를 감추기 위해 현재 이미지 흐름에 빈 텍스트 옵션이나 구현체 하나짜리 입력 Factory를 미리 추가하지 않는다. 2D 캐릭터·오브젝트의 제작 규칙은 각 기능이 구현될 때 별도 설계한다.

2D 배경의 장면 설명 기반 기준 이미지 생성은 [프롬프트 모드 설계](2026-10-08-2d-background-prompt-mode-design.md)를 따른다.
