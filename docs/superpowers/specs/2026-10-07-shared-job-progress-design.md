# 작업 진행 상태 공용 컴포넌트 설계

- 작성일: 2026-10-07
- 상태: 2026-10-07 사용자 승인, 구현 계획 작성 단계
- 기준: `main`의 `d89dfa9`에 반영된 2D 배경 진행 상태 UI
- 대상: Frontend의 2D 배경, 3D 배경, 캐릭터 작업 진행 상태

## 목적

현재 2D 배경의 진행 상태 화면을 공용 컴포넌트로 추출하고, 3D 배경과 캐릭터에도 같은 표현을 적용한다. 이후 추가되는 작업도 단계와 집계 데이터를 전달해 같은 화면을 사용한다.

사용자가 요청한 핵심 제약은 **현재 2D 화면의 모양과 동작 보존**이다. 시각적 개선을 추가로 제안할 경우 구현 전에 목업으로 확인받는다. 이번 설계는 새로운 디자인을 제안하지 않는다.

## 범위

포함하는 변경:

- 진행 상태 제목, 상태 아이콘·문구, 현재 단계, 진행 막대, 상세 펼치기·접기
- `번호 · 아이콘 · 단계 이름`의 한 줄 카드와 상태별 색상
- 성공 개수 / 대상 개수 요약과 새로고침·작업 취소 아이콘 버튼
- 2D 표시 코드 추출, 3D 배경·캐릭터의 기존 단계 컴포넌트 연결
- 구현 완료 후 Frontend 지침과 도메인 탐색 문서에 재사용 규칙 추가

작업 단계·서버 상태 전이, HTTP 계약, 생성 요청, 검수·재시도 로직, 모델 선택, 결과 화면은 변경 범위에 포함하지 않는다. 새 UI 라이브러리나 작업 종류별 등록 시스템도 추가하지 않는다.

2D 정적 작업은 5단계이며 반복 애니메이션이 포함되면 프레임 생성·검수가 추가되어 7단계다. 3D는 현재 7단계이며 선택하지 않은 작업 단계가 완료되지 않아 작업 종료 시에도 단계 완료율이 100% 미만일 수 있다. 이를 화면 통일을 위해 임의로 완료 처리하지 않는다.

## 선택한 구조

**표시는 하나로 공유하고, 작업별 단계 판단과 집계는 기존 위치에 둔다.**

계획 경로는 `apps/frontend/src/features/screens/JobProgressPanel.tsx`다. 기존 `Icon`, `Button`, `cn`, 테마 토큰을 재사용한다. `src/components/ui/`가 feature·domain을 참조하지 않는 계층 규칙을 지키기 위해 작업 화면 계층에 둔다.

기존 `SpriteProgress`, `BackgroundPipelineStepper`, `CharacterPipelineStepper`는 작업 데이터를 표시 입력으로 변환하는 얇은 연결 컴포넌트가 된다. 공용 컴포넌트 안에 2D·3D·캐릭터 분기나 서버 요청을 넣지 않는다.

비교한 대안은 작업 종류에 따라 계산까지 수행하는 단일 컴포넌트와 스타일만 공유하는 방식이다. 전자는 서로 다른 상태 규칙을 결합하고, 후자는 헤더·버튼·접근성 코드의 중복을 남기므로 선택하지 않는다.

### 표시 입력과 책임

| 입력 | 계약 |
| --- | --- |
| 작업 상태 | 서버 작업 상태를 전달; 현재 2D의 `jobStatusLabel`·상태 아이콘·색상으로 표시 |
| 단계 목록 | 안정된 ID, 이름, 아이콘, 표시 상태, 실제 완료 여부를 전달 |
| 현재 단계 | 현재 단계 ID와 헤더의 위치·단계 문구를 전달; 완료 개수와 구분 |
| revision | 2D의 기존 revision만 선택적으로 전달; 3D에 임의 값을 추가하지 않음 |
| 요약 목록 | ID, 아이콘, 이름, 표시 값, 접근성 설명을 전달; 미확정 대상도 표현 가능 |
| 행동 | 새로고침·취소 콜백과 취소 비활성 조건 전달; 취소 콜백이 없으면 취소 버튼 생략 |
| 접근성 이름 | 작업별 단계 탐색 이름을 전달; 기존 접근 가능한 이름 유지 |

공용 컴포넌트는 펼침 상태와 ARIA 연결용 ID만 로컬로 관리한다. 완료율은 전달받은 완료 단계 수 / 전체 단계 수로 계산하며 별도 서버 상태나 진행률 상태를 저장하지 않는다.

단계의 완료 여부와 표시 상태는 독립적으로 유지한다. 예를 들어 부분 성공 내보내기는 완료된 결과가 있으면서도 경고 상태를 표시할 수 있다. 작업 종료 상태만으로 모든 단계에 완료 체크를 채우지 않는다.

### 화면 구조

1. 왼쪽 헤더에 진행 상태 제목과 현재 상태, 그 아래 기존 단계·완료율·선택적 revision 표시
2. 오른쪽에 원형 새로고침·취소 버튼과 상세 펼치기·접기 버튼
3. 완료된 단계에 근거한 진행 막대
4. 현재 2D와 같은 한 줄 단계 카드와 `py-2` 간격
5. 구분선 아래 성공 요약을 양 끝에 배치하고 필요한 추가 요약 표시

현재 2D의 카드 배경·테두리·색상·글자 크기·간격·아이콘·요약 순서·반응형 배치를 추출 기준으로 삼는다. 카드에 `완료`, `대기`, `검수 대기`를 별도 줄로 다시 넣지 않으며 접근성 설명은 유지한다.

2D의 바깥 패널과 오류·재시도·검수·결과 영역은 기존 화면이 소유한다. 3D 화면의 패널도 화면 측에서 구성하되 같은 토큰과 외관을 사용한다. 기존 테스트 식별자와 단계 탐색 이름을 보존한다.

## 작업별 연결

### 2D 배경

- 기존 단계 구성, phase 보정, 완료 판정, `spriteProgressCounts`를 유지한다.
- 정적 작업의 최종 검수와 반복 애니메이션의 프레임 검수를 구분한다.
- 원본 분석·배경 이미지·프레임 성공 수는 현재 슬롯과 현재 작업 결과를 기준으로 표시한다.
- 기존 `대상 확인 중` 표현을 유지하며 대상이 미확정인 상태를 `0 / 0` 성공으로 바꾸지 않는다.
- 취소 확인 문구, 승인했을 때만 요청하는 동작, 취소 후 저장된 결과 접근을 유지한다.

### 3D 배경·캐릭터

- 각 `computeStepStates`의 검수·실패·취소·부분 성공 판정과 단계 순서를 유지한다.
- 헤더의 현재 단계 위치와 실제 완료 개수를 구분하고, 공용 막대에는 완료된 단계만 반영한다.
- 기존 진행 중 버퍼·펄스는 공용 2D 표현으로 통일한다. 진행 중 상태는 단계의 아이콘·색상·접근성 텍스트로 전달한다.
- 분석 요약은 해당 작업의 원본 분석 성공 여부 / 1로 표시한다.
- 이미지 요약은 `generationTally`의 현재 성공 수 / 생성 대상 슬롯 수를 사용한다. 배경은 파츠 이미지, 캐릭터는 방향 이미지라는 문맥에 맞는 이름을 쓴다.
- 3D 요약은 `meshTally`의 준비된 모델 수 / 제작 대상 파츠 수를 사용한다. 모든 파츠 수를 분모로 쓰지 않는다.
- 3D 생성이 선택되지 않았고 실제 제작 대상·결과도 없으면 3D 요약을 생략한다. 후속 생성으로 대상·결과가 생겼다면 모델 선택 값만 보고 숨기지 않는다.
- 생성 대상이 아직 없으면 성공률을 확정하지 않고 대상 확인 상태를 표시한다.

### 행동과 오류

공용 버튼은 화면이 전달한 콜백을 호출한다. 조회·mutation·취소 후 이동은 기존 화면이 담당한다. 종료된 작업에는 취소 콜백을 전달하지 않으며 서버 조회 오류의 기존 안내와 새로고침 행동을 유지한다.

3D에도 취소 전 native `window.confirm`을 사용한다. 확인 문구는 `작업을 취소할까요?`로 두고, 2D의 PNG·ZIP 보존 안내를 그대로 복제하지 않는다. 승인 시 기존 취소 요청을 실행하고 성공 후 기존 입력 화면 이동을 유지한다. 취소 요청 중이거나 서버 조회 오류가 있으면 취소 버튼을 비활성화한다.

3D의 [RunProgress.tsx](../../../apps/frontend/src/features/screens/background/RunProgress.tsx), [LiveActionBar.tsx](../../../apps/frontend/src/features/screens/background/LiveActionBar.tsx)에 있는 작업 취소 행동은 상단으로 모아 중복 버튼을 없앤다. 해당 영역의 나머지 진행 정보와 결과별 행동은 유지한다.

오류 이유, 재시도, 시도 횟수는 기존 상세 영역에 남긴다. 단계 카드의 고유한 시도 정보가 상세 영역에 없는 상태가 있다면 같은 정보가 보이도록 연결한다. 공용 컴포넌트 추출을 이유로 실패를 숨기거나 취소·재시도 정책을 바꾸지 않는다.

## 검증과 수용 기준

### 현재 2D 보존

리팩터링 전에 현재 코드와 Fake API로 기준 화면을 확보한다. 변경 후 동일 데이터·뷰포트·테마·글꼴·모션 조건으로 비교한다. 첨부한 실데이터 화면과 다른 Fake 데이터의 개수 차이를 시각 회귀로 판단하지 않는다.

- 정적 5단계, 반복 애니메이션 7단계, 상세 펼침·접힘
- 검수 대기, 부분 성공, 실패, 취소, 완료 및 검수 재진입
- 데스크톱·390px 모바일, 밝은 테마·어두운 테마, reduced motion
- 카드·버튼·요약의 배치와 간격 보존, 가로 넘침 없음
- 취소 확인을 닫으면 요청 0회, 수락하면 요청 1회
- 키보드 조작, 포커스, 접근 가능한 이름·현재 단계·진행 막대 값 보존

승인받은 2D 외관과 차이가 필요한 경우 먼저 목업과 변경 이유를 제시한다.

### 공용 표시와 3D 동작

- 세 작업이 같은 공용 표시 컴포넌트를 사용하고 각 연결 컴포넌트에 표시 마크업을 다시 복제하지 않는다.
- 기존 단계 계산 테스트를 유지하고 실제 수집되는 테스트로 연결 결과를 검증한다.
- 현재 `CharacterPipelineStepper.test.tsx`는 Vitest의 `*.test.ts` 수집 범위에 들어가지 않는다. 구현 시 순수 계산 테스트를 수집 가능한 파일로 정리하고 실행 결과로 확인한다.
- 이미지 슬롯·모델 대상의 분모, 부분 성공, 3D 미선택·후속 생성, 취소 확인·이동을 검증한다.
- 기존 검수·재시도·오류·결과 동작과 시도 정보가 유지되는지 확인한다.
- 새 작업은 단계·요약·행동 입력만 연결할 수 있어야 하며 공용 컴포넌트에 작업 종류 분기를 추가하지 않는다.

구현 후 저장소 루트에서 Frontend 전체 회귀를 실행한다. Fake 검증과 실제 유료 AI 호출을 구분하며 이 작업에서는 유료 호출을 실행하지 않는다.

## 구현 완료 후 지침 반영

공용 컴포넌트가 실제 구현되고 세 화면의 회귀 검증이 끝난 뒤 다음 문서를 같은 구현 변경에 포함한다. 설계 단계에서는 아직 존재하지 않는 컴포넌트를 사용하라는 현행 지침을 추가하지 않는다.

- [apps/frontend/AGENTS.md](../../../apps/frontend/AGENTS.md): 신규·수정 작업의 진행 상태 UI는 `JobProgressPanel`을 우선 재사용하고, 단계 판단·집계·서버 요청은 작업별 연결부에 둔다. 같은 헤더·막대·단계 카드·요약·행동 표시를 별도로 복제하지 않는다. 기존 2D 외관 변경은 사전 목업 승인 조건을 따른다.
- [docs/xHuman/frontend.md](../../xHuman/frontend.md): 실제 공용 파일·연결 컴포넌트·집계 함수·검증 파일과 새 작업 연결 방법을 갱신한다.

구현 계획에는 기본 실행 방식인 작업별 분담·독립 리뷰(Subagent-driven), 2D 기준 화면 확보, 공용 추출, 3D 연결, 회귀 검증, 지침 갱신의 의존 관계를 기록한다. 이 문서는 설계이며 작업별 구현 절차는 서면 설계 승인 후 별도 계획으로 작성한다.
