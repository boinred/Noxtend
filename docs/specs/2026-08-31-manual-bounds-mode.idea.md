## 한 문장

VLM의 자동 좌표 탐지를 쓰지 않고, 사람이 원본 이미지 위에 캐릭터의 모든 파츠를
직접 사각형으로 그려 이름을 붙인 뒤, VLM은 그 확정된 좌표를 입력으로 받아
`occludedBy`와 `description`만 계산하게 한다.

## 지금 방식과 무엇이 다른가

| | 지금 (main·feature/character) | 이 아이디어 |
|---|---|---|
| 파츠 목록을 정하는 주체 | Extract(VLM)가 이름을 세고 Decompose(VLM)가 좌표를 냄 | 사람이 이름·좌표를 전부 확정 |
| 사람의 개입 시점 | 접수 시 힌트(개수만), 결과 확인은 생성 후 | 접수 전에 이미지 위에서 전부 그림 |
| VLM이 하는 일 | 파츠 식별 + 좌표 + occludedBy + description | occludedBy + description **만** |
| Decompose 호출 횟수 | 1회 | 1회 (동일) |

**핵심 차이는 "누가 좌표를 정하는가" 하나다.** 나머지 파이프라인
(Analyze → Extract → Decompose → Generate 팬아웃, 큐·워커·오케스트레이터)은
그대로 둔다.

## 왜 이 방향인가

- 지금까지 나온 다른 대안들(review-gate 사후 검수, occludedBy 국소 재계산,
  전체 재-Decompose)은 전부 "자동탐지가 먼저 돌고 사람이 사후에 고친다"를
  전제했다. 그 전제 위에서는 "겹치는 파츠를 나중에 추가하면 occludedBy를
  어떻게 다시 계산하나"라는 문제가 계속 따라붙는다.
- 사람이 처음부터 전부 그리면 그 문제가 **발생하지 않는다.** Decompose가
  파츠 전체를 한 번에 보고 occludedBy를 내는 기존 원칙(§Plan D-2)이 그대로
  성립하고, 재계산·부분 병합·롤백 같은 복잡도가 통째로 사라진다.
- `docs/specs/2026-08-30-occludedby-recompute.md`의 함정 1~5 중 4개가 이
  방식에서는 성립하지 않는다.

## 검증되지 않은 전제 — 이게 이 문서의 핵심

**"자동탐지가 실제로 얼마나 틀리는가"를 모른다.** 이 값에 따라 결론이 정반대다.

| 만약 자동탐지가… | 이 아이디어의 가치 |
|---|---|
| 좌표는 대체로 맞고 가끔 파츠를 놓치는 정도 | **없음.** 사람이 20개 그리는 노동만 늘고 결과는 비슷 — 오히려 손해다 |
| 좌표가 자주 어긋나거나 분리를 잘못함(벨트가 바지에 붙는 등) | **큼.** 정확한 좌표가 생성 품질로 이어진다 |

추가로, **좌표가 정확해져도 생성 품질이 그만큼 좋아진다는 보장이 없다.**
그림 품질을 좌우하는 것은 `description`(서술)인데, 서술은 어느 쪽이든 VLM이
쓴다. 좌표만 정확해지고 서술은 그대로면 체감 차이가 작을 수 있다.

지금 있는 단서는 `character-tuning.plan.md`에 기록된 실제 관측
(depthOrder 중복으로 재시도 낭비, 파츠 분리 실패)뿐이다 — "틀리긴 한다"는
방향의 증거지만 "얼마나 자주·얼마나 심하게"는 안 적혀 있다.

## 먼저 확인할 것 (구현 전 필수)

큰 구현 전에 **비용 0에 가까운 실험으로 위 전제를 먼저 판정한다.**

1. 이미 돌린 캐릭터 작업 결과가 있으면 그 파츠 좌표를 연다 (추가 비용 없음).
   없으면 main으로 캐릭터 1건만 돌린다.
2. 원본 이미지 위에 그 좌표를 겹쳐 놓고(`PartsOverlay`가 이미 하는 일),
   사람이 눈으로 "몇 개가 틀렸나 / 어떻게 틀렸나"를 센다.
3. 판정:
   - 틀린 게 적다 → **이 아이디어를 접는다.** 구현 비용 0으로 결론.
   - 틀린 게 많다 → 미니 스펙으로 승격하고 구현한다.

이 단계를 건너뛰면 "만들고 나서야 별 차이 없다"를 알게 될 위험이 있다.

## 예상 함정 (승격 시 스펙에 옮길 것)

1. **좌표 고정 프롬프트가 이 방식의 전부다.** 사람이 확정한 좌표를 VLM이
   다시 바꾸지 않게 하면서 occludedBy·description만 받아오는 프롬프트가
   필요하다. 기존 `DecomposeCharacterSystem`은 좌표까지 산출하도록 설계돼
   있어 그대로 못 쓴다. 프롬프트 튜닝 사이클이라 실 API 검증이 여러 번
   필요할 수 있다 — 이 아이디어의 가장 큰 불확실성이다.

2. **파츠 20개를 사람이 다 그리는 노동량.** 캐릭터 하나에 파츠가 스물이면
   사각형을 스무 번 그리고 이름을 스무 번 입력해야 한다. 이 노동이 자동탐지
   교정보다 정말 싼지는 실제로 해봐야 안다. 파츠 힌트 택소노미
   (`characterPartTaxonomy`)로 이름 입력을 드롭다운화하면 줄어들 수 있다.

3. **Extract 단계의 위치가 애매해진다.** 사람이 이름을 다 정하면 Extract
   (파츠 식별)가 할 일이 없다. 건너뛸지, 아니면 "사람이 빠뜨린 것"을 찾는
   보조로 남길지 결정이 필요하다.

4. **기존 자동 모드와 공존해야 한다.** 이 모드를 전면 교체로 만들면 배경·소품
   카테고리와 기존 작업 흐름이 전부 깨진다. review-gate가 쓴 per-job 플래그
   패턴(`RequiresReview`)처럼 접수 시점 모드 선택으로 두는 것이 안전하다.

5. **review-gate와의 관계 정리가 필요하다.** 이 모드에서는 "탐지 결과를
   검수한다"는 개념 자체가 없어진다(사람이 이미 다 정했으므로). 이미 구현된
   review-gate를 이 모드에서 끌지, 아니면 "그린 것 최종 확인" 용도로 재사용할지
   결정해야 한다.

## 재사용할 수 있는 것 (이미 구현됨)

- 드래그로 사각형을 그려 0~1 정규화 좌표를 얻는 캔버스
  (`ReviewGate.tsx`) — 그리는 부분은 그대로 쓴다.
- 좌표 유효성 검사(`Bounds.IsWithinFrame`).
- 접수 시점 per-job 플래그 패턴(`RequiresReview`) — 모드 선택에 같은 방식 적용.
- 파츠 이름 택소노미(`characterPartTaxonomy`) — 이름 입력을 드롭다운으로.
