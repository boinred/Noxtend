> **실험 성격 명시.** `feature/character-tuning`에서만 시도한다. `feature/character`
> 반영 여부는 실 API 검증 뒤 별도로 결정한다(사용자 결정, 2026-08-30).
>
> **v5 = v4 + 가림 방향 재설계** (2026-08-31, 독립 리뷰 2회차). v4의 면적 규칙은
> 이 코드베이스의 실제 파츠에서 반례가 나왔고, 하필 이 기능이 가장 잘 쓰일 파츠에서
> 틀렸다(§배경). 가림 방향을 사람이 확인·수정할 수 있게 바꿨다.
>
> **v6 = v5 + 엣지케이스 반영** (2026-08-31, 독립 리뷰 3회차). 새 엔드포인트·`occludes`
> 필드가 기존 코드와 부딪히는 지점 12건을 반영했다.

## 배경 — v1~v4를 거쳐 온 경위

검수 게이트(`2026-08-28-review-gate.md`) 1차 구현은 겹치는 위치에 파츠를 추가하는 것을
막았다. 벨트를 바지 위에 추가하면 바지의 `occludedBy`와 서술을 다시 계산해야 하는데
그 수단이 없었기 때문이다. 그런데 **벨트/바지야말로 사람이 고치고 싶은 대표 사례**라,
이 가드가 있는 한 검수 게이트가 풀려는 문제를 못 푼다.

| 안 | 방식 | 버린 이유 |
|---|---|---|
| v1 | 충돌 집합만 묶어 새 프롬프트로 occludedBy 재계산 | 새 프롬프트·부분집합 검증·depthOrder 재정렬까지 새 코드가 과다 |
| v2 | `ApplyParts`로 이름만 갈아끼우고 Decompose 전체 재실행 | 사람이 그린 좌표가 버려지고, 손 안 댄 파츠 좌표까지 흔들린다 |
| v3 | occludedBy는 코드가 계산, 서술만 LLM. 방향은 "나중에 추가한 쪽이 가림" | 그리는 순서에 의존 — 버클을 먼저 그리면 틀린다 |
| v4 | 방향을 면적으로 판정 ("작은 쪽이 큰 쪽을 가림") | **아래 참조** |
| **v5** | **방향은 기본 추정 + 사람이 확인·수정** | — |

### 기하 정보만으로는 가림 방향을 정할 수 없다 (v4를 버린 이유)

`Bounds`는 축정렬 사각형이다(`SceneSpec.cs:92-105`). **가늘고 비스듬한 파츠는 실제
면적이 작아도 bbox 면적은 거대하다** — 어깨에서 허리로 가로지르는 가방 스트랩의 bbox는
상의 bbox와 맞먹는다. 그런데 이런 얇은 파츠가 정확히 VLM이 놓쳐서 사람이 그리게 되는
파츠다. **면적 규칙은 이 기능이 실제로 쓰이는 케이스에서 가장 잘 틀린다.**

이 코드베이스가 아는 파츠로 확인한 반례(택소노미 `characterPartTaxonomy.ts:57-98`,
자동 분리 파츠 `SeedPrompts.cs:590-621` 기준):

| 파츠 쌍 | 진실 | 면적 규칙 | 사람이 추가할 가능성 |
|---|---|---|---|
| 가방 스트랩 → 상의 | 스트랩이 가림 | **반대** | **높음** |
| 겉옷 → 상의 | 겉옷이 가림 | **반대** | 중간 |
| 머리카락 → 머리 | 머리카락이 가림 | **반대** | 낮음 |
| 벨트 → 하의 | 벨트가 가림 | 맞음 | 높음 |
| 버클·목걸이·귀걸이 | 악세사리가 가림 | 맞음 | 높음 |

"머리카락이 머리를 가린다"는 상상이 아니라 `DecomposeCharacterSystem`
(`SeedPrompts.cs:704-710`)이 가림 사례로 직접 열거한 문장이다 —
`or hair covering the scalp`.

**대안도 전부 막혔다**: 포함비 비교는 스트랩에서 양쪽 다 ≈1로 동률이고,
`OverlapCoefficient`는 대칭이라(`BoundsTests.cs:45-51`이 단언) 방향을 못 낸다.
카테고리 레이어 표는 `category`가 자유 입력 텍스트박스라(`ReviewGate.tsx:188-190`)
표에 없는 문자열이 조용히 기본값으로 떨어진다.

근본 원인: **"벨트가 바지 위"는 착장 순서라는 의미 정보이고, 축정렬 사각형 두 개에는
그 정보가 들어 있지 않다.**

### v5가 택한 것 — 기본 추정 + 사람 확인

```
기본 추정: 사람이 추가한 파츠가 겹치는 기존 파츠를 가린다
확인 수단: 겹친 파츠 목록을 전체 체크된 상태로 보여주고, 검수자가 틀린 것만 푼다
```

기본값이 맞는 벨트·버클·목걸이에서는 **클릭 0회**다. 스트랩·겉옷처럼 틀리는 경우에
검수자가 볼 기회를 얻는다. 이 기능의 존재 이유가 "사람이 VLM을 고친다"인데, 고치는
화면에서 가림 방향만 사람 손이 못 닿게 막을 이유가 없다.

`depthOrder`는 읽지도 쓰지도 않는다 — `occludedBy`는 두 파츠 사이의 관계라 전역 순서를
거칠 이유가 없고, `df5449d`가 캐릭터에서 그 값을 의미 없다고 결론 냈다.

### LLM이 하는 일

`description` 하나뿐이다. **응답 스키마에서 `bounds`를 빼면 모델이 좌표를 어길 방법
자체가 없다.**

## 목표 (한 문장)

검수 화면에서 겹치는 위치에 파츠를 추가할 수 있게 하되, 가림 방향은 코드가 추정하고
사람이 확인하며, 가려지게 된 파츠의 서술만 승인 시점에 한 번 LLM으로 다시 쓴다.

## 파이프라인 상 위치

```
Analyze → Extract → Decompose → [검수 대기] → Generate 팬아웃 → Reconstruct
                                     │
                                     ├ 파츠 추가/삭제 (겹침 허용, 즉시 무료)
                                     └ 승인 → 서술 재작성 1회 → 팬아웃
```

## 입력 → 출력

### 1. 겹치는 파츠 추가 — 즉시 반영, LLM 호출 없음

먼저 겹침만 조회해 화면이 체크박스를 그린다.

```json
POST /api/jobs/{jobId}/review/parts/overlaps
{ "bounds": {"x":0.28,"y":0.55,"w":0.44,"h":0.1} }

200 { "overlapping": ["하의", "상의"] }
```

**순수 조회다 — DB 를 바꾸지 않는다.** `Bounds.OverlapCoefficient` 계산이 전부이고
LLM 호출도 쓰기도 없다. 다만 가드는 추가 경로와 같아야 한다:

```
- Status != PendingReview 면 409 (V-6)
- bounds 가 IsWithinFrame 이 아니면 400 (V-4) — 추가 시점에 가서 실패하는 것을 막는다
- 겹치는 게 없으면 200 { "overlapping": [] } — 화면은 체크박스를 안 그리고 바로 추가한다 (V-5)
```

**호출 시점은 드래그가 끝난 뒤 1회다.** `draftBounds` 는 `onMouseMove` 마다 갱신되므로
(`ReviewGate.tsx:97-104`) 그 변화에 조회를 걸면 드래그 한 번에 수십 번 요청이 나가고
체크박스가 깜빡인다. `onMouseUp`(`:106-109`) 이후로 못박는다.

검수자가 확인·수정한 목록을 담아 추가한다.

```json
POST /api/jobs/{jobId}/review/parts
{ "name": "벨트", "category": "Belt", "bounds": {...},
  "occludes": ["하의"] }          ← 상의는 스치기만 해 체크 해제됨
```

기존 `AddReviewPart`에서 겹침 거부(`PipelineJob.cs:718-723`)를 걷어낸다.

```
0. 이름 유일성 검사 — 이미 있는 이름이면 409 (§함정3)
1. occludes 의 각 이름이 실제로 겹치는 파츠인지 검증 — 아니면 400
   (검증 없이 받으면 화면이 본 것과 다른 관계가 저장된다)
2. occludes 에 든 파츠의 occludedBy 에 새 파츠 이름을 넣는다
3. 그 파츠들을 descriptionsStale 에 기록
```

**`occludes` 는 nullable 이다 — 생략과 빈 배열이 다른 뜻이다 (V-1).**

| 값 | 뜻 |
|---|---|
| 필드 생략 (`null`) | 기본 추정을 써라 → 겹치는 것 전부를 가린다 |
| `[]` | 아무것도 안 가린다 → 검수자가 전부 해제했다 |

C# 에서 `string[]` 으로 받으면 빈 배열이 조용히 기본 추정으로 처리되어 **정반대 결과**가
된다. `string[]?` 로 받고 `null` 검사로 갈라야 한다.

```json
201 { "id": "...", "name": "벨트", "source": "manual",
      "occludes": ["하의"], "descriptionsStale": ["하의"] }
```

### 2. 파츠 삭제 — 참조 정리 포함

```
DELETE /api/jobs/{jobId}/review/parts/{partId}
```

파츠를 지울 때 세 가지를 함께 한다.

```
1. 남은 모든 파츠의 occludedBy 에서 그 이름을 제거 (리뷰 5번)
2. 그 파츠들을 descriptionsStale 에 다시 넣는다 — 서술이 "벨트에 가린" 상태로 남아 있다
3. 삭제한 파츠 자신의 이름을 descriptionsStale 에서 제거 (리뷰 3회차 1번)
```

**3번이 없으면 작업 전체가 실패한다.** 벨트 추가(하의 stale) → 버클 추가(벨트 stale) →
벨트 삭제 순서로 조작하면 stale 에 존재하지 않는 "벨트"가 남는다. 승인 시 §함정6 의
"대상 이름이 전부 있는가" 검증에 걸려 재작성 공정이 실패하고,
`ReconcileFromTasks:953-961` 이 non-Generate 실패를 blocking 으로 처리해 작업이 `Failed`
가 된다.

### 3. 승인 — 서술 재작성 1회 후 팬아웃

```
POST /api/jobs/{jobId}/review/approve
```

`descriptionsStale`이 비어 있으면 지금처럼 곧바로 팬아웃한다(호출 0회).
비어 있지 않으면 **그 파츠들만** 묶어 서술 재작성 공정 하나를 계획·적재한다.
편집을 몇 개 했든 승인당 1회다.

**재작성 프롬프트가 받는 것 / 내는 것**

| | 내용 |
|---|---|
| 입력 | 원본 이미지, 대상 파츠의 현재 서술, 그 파츠를 가리는 파츠들의 이름·서술 |
| 출력 | `[{ "name": "하의", "description": "..." }]` — **`bounds`·`depthOrder` 없음** |

좌표를 안 물어보므로 좌표가 흔들릴 수 없다. **다만 이는 LLM에 대한 보장일 뿐이므로,
반영 코드도 좌표를 못 건드리게 막는다(§구현 범위 4).**

## 구현 범위 (v3에서 통째로 빠졌던 것 — 리뷰 2·3·6·7·8번)

이 절이 없어서 v3의 규모 추정이 틀렸다. 도메인·API 외에 아래가 전부 필요하다.

**1. `descriptionsStale` 영속화 — DB 마이그레이션 필요**
파츠 추가(요청 A)와 승인(요청 B)은 별개 HTTP 요청이라 그 사이 DB에 남아야 한다.
`IStage.BuildVariables(PipelineJob job)`(`IStage.cs:27`)가 job 하나만 받으므로,
재작성 공정이 대상 파츠를 알 방법은 job 상태뿐이다. `RequiresReview`가 컬럼 +
마이그레이션(`20260829163353_ReviewGateFields`)을 받은 것과 같은 방식으로 처리한다.

**2. 새 `TaskKind` 배선 일체**

| 항목 | 없으면 |
|---|---|
| `TaskKind` enum 값 | — |
| `IStage` 구현체 + DI 등록 | `StageRegistry`가 `ProviderCallFailedException` (`IStage.cs:60`) |
| **(kind, category)별 프롬프트 시드 마이그레이션** | `RunTaskHandler.cs:105-107` "활성 프롬프트가 없습니다"로 실패 |
| `FakeLlmProvider.Canned` 케이스 (`:103-107`) | 기존 테스트·E2E가 이 경로에서 죽는다 |

**3. 재시도 화이트리스트 확장** (사용자 결정, 2026-08-31)
`RetryOutputTask`(`PipelineJob.cs:434-438`)가 `Generate`·`Reconstruct`만 허용한다.
재작성 공정을 여기 추가하고 검수 화면에 재시도 경로를 연결한다 — 그렇지 않으면 검수자가
그린 좌표가 복구 불가능하게 사라진다.

**4. 서술 전용 mutator 신설**
`AssetPart.ApplyDetail`(`AssetPart.cs:108-119`)은 `_placements.Clear()` 후 재삽입하고
`DepthOrder`·`OccludedBy`까지 덮어쓴다. 재작성 반영에 이걸 재사용하면 **사람이 그린 좌표가
지워지는데 아무도 못 잡는다** — 팬아웃은 좌표를 안 보므로 정상 진행되고, 조립 단계에서야
드러난다(리뷰 6번). `Description`만 바꾸는 메서드를 새로 만들고 `ApplyDetail`은 이 경로에서
쓰지 않는다.

**5. Jobs 동시성 토큰** (리뷰 8번 — 리뷰어가 추론이라고 밝힌 항목이나 v5에서 손상 범위가 커진다)
Tasks에는 `RowVersion`이 있으나(`PipelineJobConfiguration.cs:93`) Jobs에는 없다. "추가"
직후 "전체 승인"이 겹치면(더블클릭·느린 네트워크) 팬아웃 계획 후에 파츠가 붙고 **그 파츠만
Generate 공정 없이 남는다** — `PlanGenerationFanOut:261-264`가 이후 즉시 return하므로
영원히 안 생긴다. Jobs에 `RowVersion`을 추가한다.

**6. 가림 방향 확인 UI** (v5 신규)
사각형을 그리면 겹친 파츠 목록을 전체 체크된 상태로 보여주고, 검수자가 해제한 결과를
`occludes`로 보낸다. `ReviewGate.tsx`에서 함께 고칠 것:

| 위치 | 변경 |
|---|---|
| `:138-140` 안내문 | "겹치는 위치는 추가할 수 없습니다" — **v6와 정반대다.** 방향을 문장으로 바꾼다("벨트가 하의를 가림", §함정4) |
| `:82-87` `resetDraft` | 체크박스 상태 초기화 추가 — 안 하면 다음 사각형에 이전 선택이 남는다 |
| `:118` 이름 입력 | `trim()` 은 이미 한다. 백엔드도 같은 정규화를 해야 한다(§함정3) |

**7. e2e 목 서버·기존 테스트 교체** (리뷰 3회차 2번)
`review-gate.spec.ts:55`의 `#2 기존 파츠와 겹치는 사각형은 400 으로 거부된다`는 이 스펙이
없애려는 동작을 고정하고 있다 — **반드시 삭제·교체한다.** `fakeApi.ts:1344-1352`의
`PART_OVERLAPS_EXISTING` 400 응답도 함께 걷어내고, `POST /review/parts/overlaps` 라우트를
새로 추가한다(지금은 어디에도 안 잡혀 e2e가 미스한다).

## 이번에 안 하는 것 (제외 범위)

- **기존 파츠끼리의 가림 방향 수정** — 1차 Decompose가 낸 `occludedBy`는 그대로 둔다.
  사람이 추가한 파츠와 겹치는 쌍만 이번 스펙이 다룬다.
- **반대 방향(기존 파츠가 새 파츠를 가림) 표현** (V-2) — 체크 해제는 "관계 없음"만 뜻하고
  "반대 관계"는 표현할 수 없다. 최악이 **누락**이고 틀린 관계가 저장되지는 않으므로
  §함정1의 "조용히 틀린다" 부류를 만들지 않는다.

  **실제 반례는 등에 멘 가방 몸체다** — 택소노미의 `가방`(`characterPartTaxonomy.ts:97`)은
  자동 분리에서 몸체/스트랩/버클로 쪼개지는데(`SeedPrompts.cs:591-592`), 정면 뷰에서
  몸체는 몸통에 가려져 VLM 이 놓치기 쉽고 사람이 추가하면 진실은 "몸통이 가방을 가린다"다.
  나중에 반대 방향을 붙일 때 이 사례를 기준으로 설계하면 재설계를 피할 수 있다.
- **삭제 후 원래 서술 복원** — 삭제한 파츠를 `descriptionsStale`에 다시 넣어 재작성으로
  해결한다. 원래 서술을 보관해 되돌리는 방식은 쓰지 않는다(보관 상태가 하나 더 늘어난다).
  단, `occludedBy` 참조 정리는 미루지 않는다(§입력→출력 2).
- **좌표 수정** — 검수에서 기존 파츠의 좌표를 옮기는 기능은 만들지 않는다. 추가·삭제만이다.
- **한 파츠에 사각형 여러 개** — 사람이 그리는 사각형은 파츠당 1개다. 대칭 파츠(귀걸이)
  한쪽만 추가되는 경우가 생기면 그때 연다.
- **`feature/character` 반영 판단** — 실 API 검증 뒤 별도 결정.

## 예상 함정

1. **🔴 팬아웃 가드의 조건은 "미완료"가 아니라 "성공하지 않음"이다.** `ApproveReview`가
   `Status = Running` + `ReviewApproved = true`로 바꾸므로 기존 가드
   (`RequiresReview && !ReviewApproved`, `:283`·`:929`)는 승인 후 안 막는다. 새 가드를
   `!IsTerminal`로 쓰면 **재작성이 Failed일 때 가드가 열려** 옛 서술로 이미지가 나간다.
   지금은 `JobOrchestrator.cs:44-48`의 Plan → Reconcile 순서 덕에 우연히 과금이 안 나지만
   호출 순서에 기댄 안전이다(리뷰 4번).

   ```
   조건: 재작성 공정이 존재 && 그 공정의 Status != Succeeded  → 팬아웃 금지
   ```

2. **🔴 반대로 가드가 안 풀리면 이미지 0장짜리 작업이 조용히 성공한다.**

   인과는 이렇다. 재작성이 성공했는데 가드가 팬아웃을 계속 막으면 → Generate 공정이
   **하나도 계획되지 않는다** → `ReconcileFromTasks:978-985`가 출력 공정 목록을 훑어
   `All(Succeeded)`를 판정하는데, **빈 배열에 대한 `All`은 참이다**(공허참) → 이미지가
   한 장도 없는 작업이 `Succeeded`로 확정된다.

   실패가 아니라 **성공으로 끝나기 때문에** 아무도 눈치채지 못한다. 사용자는 완료된
   작업을 열어보고 나서야 빈 결과를 발견한다.

   이건 새 위험이 아니라 **재발 경로다.** review-gate 1차 구현 때 같은 공허참 문제를
   찾아 가드를 넣고 `PipelineJob.cs:936-941`에 주석까지 남겼다. 이번 스펙이 가드를 하나
   더 얹으므로 그 조건이 안 풀리는 경로가 새로 생긴다.

   §함정1과 §함정2는 **같은 가드의 양쪽 끝이다** — 함정1은 "너무 일찍 열림"(과금),
   함정2는 "안 닫힘 아니라 안 열림"(빈 성공). 테스트도 양쪽 다 필요하다(리뷰 10번).

3. **이름 유일성이 이 설계의 전제다.** `occludedBy`·`descriptionsStale`·재작성 응답이
   전부 이름을 키로 쓰는데, `AddReviewPart`에는 이름 중복 검사가 없다(핸들러·컨트롤러에도
   없음). `ValidatePartDetails`의 중복 검사(`:782-791`)는 Decompose 경로 전용이라 이
   경로를 안 탄다. 가드를 추가한다(리뷰 1번).

   **비교 전에 `trim()`한 뒤 정확 일치로 본다.** 프론트는 이미 `trim()`을 하지만
   (`ReviewGate.tsx:118`) 백엔드는 `name`을 그대로 쓴다(`PipelineJob.cs:739-740`). API를
   직접 부르면 `"벨트"`와 `"벨트 "`가 둘 다 통과해, §함정3이 막으려던 상태에 그대로
   도달한다(리뷰 3회차 3번).

4. **기본 추정이 틀렸는데 검수자가 그냥 넘어갈 수 있다.** 전체 체크가 기본이므로 스트랩·
   겉옷 케이스에서 아무 생각 없이 승인하면 v4와 같은 잘못된 결과가 된다. UI가 방향을
   문장으로 보여줘야 한다("벨트가 하의를 가림" — "겹침"이 아니라).

5. **겹침 임계값 0.15는 실측 전 잠정치다**(review-gate T-03). 낮으면 스치는 파츠까지
   목록에 올라 체크 해제 노동이 늘고, 높으면 실제 가림을 놓친다. 실 데이터로 조정한다.

6. **`ValidatePartDetails`는 이 경로에 그대로 못 쓴다.** 전체 목록 1:1 전제다
   (`:795` 개수 일치). 서술 재작성은 부분집합을 받으므로 별도의 가벼운 검증(대상 이름이
   전부 있는가, 빈 서술이 아닌가)이 필요하다.

7. **재작성 실패 시 검수 내용을 잃을 수 있다.** 재시도 대상에 넣어(§구현 범위 3) 복구
   경로를 열지만, 재시도까지 소진하면 작업이 `Failed`가 되고 사람이 그린 좌표도 사라진다.
   화면에 명시한다. `df5449d`로 실패 원인 1위(depthOrder 중복)가 캐릭터에서 사라져 확률은
   낮아졌다.

8. **겹침 조회와 추가 사이에 파츠가 바뀔 수 있다** (V-3). 조회로 목록을 받고 검수자가
   체크하는 동안 다른 탭에서 그 파츠가 삭제되면, 추가 시점에 `occludes`의 이름이 더 이상
   겹치는 파츠가 아니어서 400이 난다. §함정9의 검증이 잡아주지만 사용자에게는 영문 모를
   오류다 — 화면이 이 400을 받으면 겹침을 재조회하고 목록을 다시 그려야 한다.

9. **`occludes` 검증을 빠뜨리면 화면과 저장이 어긋난다.** 클라이언트가 겹치지도 않는
   파츠 이름을 보내면 그 파츠의 서술이 근거 없이 깎인다. 서버가 겹침을 다시 판정해
   검증한다(§입력→출력 1의 1단계).

## 검증 방법

**가드 (§함정1·2 — 이 스펙에서 가장 비싼 실수 지점)**
- 🔴 재작성 공정이 **미완료**인 동안 `PlanGenerationFanOut`·`ReconcileFromTasks`를 불러도
  Generate가 계획되지 않고 작업이 종료로 안 빠짐.
- 🔴 재작성 공정이 **Failed**인 동안에도 Generate가 계획되지 않음(§함정1의 실제 구멍).
- 🔴 재작성 공정이 **Succeeded**하면 팬아웃이 재개되고, 작업이 이미지 0장으로 Succeeded
  되지 않음(§함정2).

**가림 방향·이름**
- `occludes`를 준 대로 그 파츠들만 `occludedBy`가 갱신됨.
- `occludes`를 **생략**하면 겹치는 파츠 전부가 갱신됨(기본 추정).
- `occludes: []`이면 **아무 파츠도** 갱신되지 않고 `descriptionsStale`도 비어 있음
  — 생략과 빈 배열이 다르게 처리됨을 고정한다(V-1).
- 겹치지 않는 파츠 이름을 `occludes`에 넣으면 400(§함정9).
- 무관한 파츠를 먼저 그리든 나중에 그리든 가림 판정이 같다(추가 순서 비의존 회귀 고정).
  **완전한 순서 비의존은 성립하지 않는다** — 버클을 먼저 그리면 그 뒤에 그린 벨트가
  "버클이 나를 가린다"를 표현할 방법이 없다(§제외 범위의 반대 방향 미지원). 구현 중
  발견해 이 항목을 좁혔다(2026-09-01).
- 이미 있는 이름으로 추가하면 409(§함정3).
- `"벨트"`가 있을 때 `"벨트 "`(뒤 공백)로 추가하면 409 — 정규화 후 비교(리뷰 3회차 3번).

**겹침 조회**
- 검수 대기가 아닌 작업에 조회하면 409(V-6).
- 화면 밖 좌표로 조회하면 400(V-4).
- 겹치는 게 없으면 빈 배열(V-5).
- 🔴 조회 전후로 job·파츠 상태가 **전혀 바뀌지 않음** — 순수 조회임을 고정한다.
  실수로 저장하면 조용히 상태가 오염된다.

**삭제**
- 벨트 추가 후 삭제하면 하의의 `occludedBy`에서 "벨트"가 사라지고, 하의가 다시
  `descriptionsStale`에 들어감(리뷰 5번).
- 🔴 벨트 추가 → 버클 추가(`occludes=[벨트]`) → 벨트 삭제 순서로 조작해도
  `descriptionsStale`에 "벨트"가 남지 않음. 이후 승인이 작업을 `Failed`로 만들지 않음
  (리뷰 3회차 1번).

**일괄·비용**
- 편집 5개 후 승인 시 재작성 공정이 **1개만** 계획됨.
- `descriptionsStale`이 비면 승인 즉시 팬아웃(불필요한 호출 0회).
- 겹치는 파츠 추가 자체는 LLM 호출 0회.

**반영**
- 재작성 반영 후에도 모든 파츠의 `Placements`가 그대로임(§구현 범위 4 회귀 고정).
- 재작성 공정이 재시도 가능함(§구현 범위 3).

**동시성**
- 파츠 추가와 승인이 경합하면 뒤늦은 쪽이 거부됨(§구현 범위 5).

**e2e·실 API**
- e2e: 겹치는 사각형을 그려 체크박스가 뜨고, 하나를 해제하고 추가하면 그 파츠만
  `occludedBy`가 갱신되는 흐름. **체크박스 문구가 방향을 밝히는지도 확인한다**
  ("벨트가 하의를 가림" — 단순 "겹침"이 아니라, §함정4).
- e2e: 기존 `#2 기존 파츠와 겹치는 사각형은 400 으로 거부된다`(`review-gate.spec.ts:55`)를
  삭제하고 위 흐름으로 교체(§구현 범위 7).
- **실 API 1회**: 벨트/하의가 실제로 겹치는 소스로 벨트 추가 → 승인 → 생성된 하의
  이미지에 벨트가 중복해 그려지지 않는지 육안 확인. **이 스펙의 유일한 최종 판정 기준이다.**

## 이 스펙이 받아들인 것 (해결하지 않는 문제)

- **1차 Decompose가 낸 좌표가 틀렸으면 그대로 굳는다.** 좌표를 다시 계산하지 않으므로
  VLM의 1차 오류는 남는다. 사람이 검수 화면에서 확인하고 승인한 결과이므로 받아들인다
  (사용자 결정, 2026-08-31).
- **서술 재작성 품질은 LLM에 달려 있다.** 좌표는 지켜지지만 "벨트에 가린 부분을 빼고
  써라"를 모델이 얼마나 잘 따르는지는 실 API로만 안다.
- **가림 방향의 최종 책임은 사람에게 있다.** 코드는 추정만 하고 판정하지 않는다 —
  기하 정보만으로는 원리적으로 불가능하다는 것이 v4의 결론이다.
- **같은 배치 안에서 재작성 대상이 서로를 참조하면 옛 서술을 본다.** 벨트 추가(하의
  stale) → 버클 추가(벨트 stale) 순서면, 하의 재작성이 **갱신 전 벨트 서술**을 입력으로
  받는다. "승인당 1회"를 못박았으므로 순차 처리는 하지 않는다. 실패가 아니라 품질 저하라
  조용하다 — 실제로 문제가 되는지 실 API 결과를 보고 판단한다(리뷰 3회차 4번).
