# 미니 스펙: 큐 회수가 실제로 재처리되게 한다 (queue-reclaim)

> **이 브랜치의 작업과 무관한 기존 결함이다.** `git log origin/main..HEAD -- .../Queue/`
> 가 비어 있다 — 검수 게이트는 큐 코드를 한 줄도 건드리지 않았다. 오늘 조건이 맞아
> 드러났을 뿐이다.

## 관측된 문제

같은 이미지로 접수한 작업의 `Extract` 가 11분간 `Pending` 에 멈춰 있었다. 재시작
전까지 풀리지 않았다.

```
noxtend:tasks:extract
  XLEN 8 · entries-read 5 · lag 3        ← 3건이 배달조차 안 됨
  pending 1 · idle 51초 · delivery-count 3
```

`delivery-count 3` 은 스위퍼가 두 번 회수했다는 뜻인데 **재처리는 0회**였다.
`LlmCalls` 에 그 시각 이후 Extract 행이 없고, API 로그에도 결과 줄이 없다.

## 원인 — 회수한 메시지를 아무도 읽지 않는다

`RedisTaskQueue` 는 싱글턴이다(`InfrastructureServiceCollectionExtensions.cs:208`).
따라서 컨슈머 이름이 프로세스당 하나다(`RedisTaskQueue.cs:31`).

```csharp
// 회수 — 오래된 메시지를 "이 워커" 앞으로 옮긴다 (:138)
await db.StreamClaimAsync(streamKey, ConsumerGroup, _consumerName, ...);

// 소비 — 새 메시지만 읽는다 (:53)
await db.StreamReadGroupAsync(streamKey, ConsumerGroup, _consumerName, ">", count: 1);
```

`XCLAIM` 은 메시지를 **PEL(pending entries list)** 에 남긴 채 소유자만 바꾼다.
`">"` 는 **아직 아무에게도 배달되지 않은** 메시지만 준다. 그래서 회수된 메시지는
영원히 다시 읽히지 않는다.

**클래스 주석이 약속하는 것이 실제로는 없다** (`RedisTaskQueue.cs:18-22`):

> 사라진 메시지는 pending 목록에 남고 `ReclaimStaleAsync` 가 회수한다 …
> 큐를 잃어도 작업을 잃지 않는다

오늘 재시작으로 풀린 것은 회수가 동작해서가 아니라 **새 파드가 새 컨슈머 이름으로
시작해 `">"` 읽기가 새 메시지를 받았기 때문**이다.

**테스트가 못 잡는 이유**: `InMemoryTaskQueue` 가 이 동작을 흉내내는데, 그쪽은 PEL 이
없어 회수하면 곧바로 다시 꺼내진다. 실제 Redis 에서만 갈린다.

## 목표 (한 문장)

워커가 죽거나 메시지를 물고 놓지 않아도, 스위퍼가 회수한 메시지를 워커가 실제로 다시
집어 처리한다.

## 입력 → 출력

바뀌는 것은 `RedisTaskQueue` 의 소비 루프 하나다.

```
지금:  XREADGROUP ... ">"                        새 메시지만
바꿈:  ① XREADGROUP ... "0"  → PEL 에 남은 내 메시지부터 (없으면 빈 배열)
       ② 없으면 XREADGROUP ... ">"               새 메시지
```

`"0"` 은 **이 컨슈머 앞으로 배달된 미확인 메시지**를 준다. 스위퍼가 `XCLAIM` 으로
옮겨 둔 것이 여기 들어온다.

한 바퀴에 ①을 먼저 보고, 빌 때만 ②로 간다 — 밀린 것을 새 것보다 먼저 처리한다.

## 이번에 안 하는 것 (제외 범위)

- **워커 수 늘리기** — 별개 문제다(§관련 결함 A). 회수가 동작하면 막혀도 스스로 풀리므로
  급하지 않다. 측정 없이 동시성부터 올리지 않는다(이 저장소가 `Generate`·`Reconstruct`
  에서만 여럿을 쓰는 것과 같은 판단).
- **텍스트 LLM 타임아웃 분리** — 별개 문제다(§관련 결함 B).
- **취소 시 진행 중 호출 끊기** — 별개 문제다(§관련 결함 C).
- **컨슈머 이름을 워커마다 나누기** — `ITaskQueue` 의 수명을 싱글턴에서 바꾸는 일이라
  범위가 커진다. `"0"` 읽기만으로 이번 증상은 해소된다.

## 예상 함정

1. **🔴 같은 메시지를 두 번 처리하면 과금이 겹친다.** PEL 을 읽으면 이미 한 번
   처리했으나 Ack 만 못 한 메시지가 올 수 있다. 실행 계층에
   `RunTaskHandler`·`RunGenerationTaskHandler` 가 이미 상태 기반 멱등 판정을 갖고
   있는지 확인하고, 없으면 이번 스펙에서 막는다. **여기가 이 스펙에서 가장 비싼
   실수 지점이다.**

2. **PEL 을 먼저 읽으면 독성 메시지에 갇힐 수 있다.** 처리할 때마다 죽는 메시지가
   PEL 에 있으면 워커가 그것만 무한히 다시 집는다. `delivery-count` 상한을 두고
   넘으면 Ack 하고 버린다 — 작업 정본은 DB 이고 스위퍼가 재적재하므로 잃지 않는다.

3. **`"0"` 읽기는 매번 전체 PEL 을 훑는다.** `count: 1` 로 제한하되, 빈 배열이 올
   때까지 매 바퀴 도는 비용을 확인한다.

4. **회수 대상이 아직 살아 있는 워커의 것일 수 있다.** `idleLongerThan` 이 리스보다
   짧으면 정상 처리 중인 메시지를 뺏는다. `ReclaimPlan` 의 값과 리스 갱신 주기를
   대조한다.

5. **인메모리 큐가 이 차이를 못 흉내낸다.** 이번 변경의 검증은 실 Redis 테스트가
   있어야 한다. `SqlServerFixture` 처럼 Testcontainers 로 Redis 를 띄우는 픽스처가
   필요할 수 있다.

## 검증 방법

- 🔴 실 Redis: 메시지를 소비하고 Ack 하지 않은 채 컨슈머를 버린 뒤, 스위퍼 회수를
  돌리고 **새 소비 루프가 그 메시지를 다시 집는지** 확인. 지금 코드로는 실패해야 한다.
- 🔴 실 Redis: 같은 메시지가 두 번 배달돼도 공정이 두 번 실행되지 않음(§함정1).
- 실 Redis: `delivery-count` 상한을 넘긴 메시지는 Ack 되고 루프가 다음으로 넘어감(§함정2).
- 회귀: 정상 경로(새 메시지만 있는 상태)에서 소비 순서·성능이 그대로임.
- 재현 시나리오: 워커가 응답을 기다리는 동안 파드를 죽이고, **재시작 없이** 스위퍼만으로
  그 공정이 다시 도는지 확인 — 오늘 실패한 바로 그 경로다.

## 관련 결함 (이번 범위 밖, 따로 판단)

**A. 텍스트 워커가 1대다** (`TaskWorkerRegistration.cs:65-70`)
`Generate`·`Reconstruct` 만 여럿이고 나머지는 `_ => 1`. 느린 호출 하나가 그 단계 전체를
막는다. 오늘 증상의 직접 원인이지만, 회수가 동작하면 스스로 풀리므로 후순위다.

**B. LLM HttpClient 타임아웃이 20분이다** (`InfrastructureServiceCollectionExtensions.cs:100`)
3D 공급자는 120·180초인데 LLM 만 20분이고, 텍스트·이미지가 같은 클라이언트를 쓴다.
텍스트 실측은 9~51초다. 텍스트만 2~3분으로 분리하면 A 의 영향 시간이 짧아진다.

**C. 취소해도 진행 중 호출이 안 끊긴다**
DB 상태만 `Canceled` 가 되고 나간 HTTP 요청은 계속된다. 낭비 비용이 그대로 나간다.
`TaskExecution` 의 취소 감시가 실제로 `cts` 를 끊는지 확인이 필요하다.
