가지 않기 위해서다.

## 좌표 문제 — 주 과제

### 증상

Decompose 가 내는 파츠 bbox 가 틀린다. **처음엔 "허리 아래로 갈수록 밀린다" 로 봤으나
2026-09-03 실측으로 틀린 진단이었음이 드러났다** — 아래 §2026-09-03 실측 참고.
실제 증상은 긴 파츠(상의·하의)의 아래 끝이 짧게 잡히는 것이다.

### 두 번의 실패

1. **workstream O** — "인물의 topmost/bottommost 픽셀을 찾아 베이스바디 상자로 삼아라".
   전신 일러스트에서 그 범위는 프레임 거의 전체라, 베이스바디가 0.025~0.995 로 나왔다.
   **문면이 그렇게 시킨 결과다.** 되돌렸다.
2. 규칙을 좁게 겨냥해 다시 얹으려 했으나, "덧붙이기를 또 하지 말고 원인부터" 로 중단.

### 조사 결론 (서브에이전트, 근거는 DB 실측)

**모델은 재고 있지 않다.** workstream O 에서 "신발은 발보다 아래로 안 내려간다" 를 지키라고
했더니 신발을 올린 게 아니라 **베이스바디를 프레임까지 늘려서** 지켰다. 자기 사전확률
(신발 → y≈0.99)은 건드리지 않고 자유변수를 움직인 것이다.

**세로 오차의 지배 성분은 전역 스케일 하나다.** 모델이 위쪽 앵커(이미지 콘텐츠 상단)와
아래쪽 앵커(프레임 하단 1.0) 사이를 비례로 채우는데, 실제 인물은 0.935 에서 끝난다.
검산: 전체 좌표에 `y × 0.935/0.995` 를 곱하면 머리 0.049→0.046(실측 0.044), 신발 바닥
0.991→0.931.

**좌우 혼동은 다리에만 있다.** 팔·어깨·손 조각은 전부 좌우가 일관된다. 깨진 것은 오른쪽
다리 하단 두 조각뿐이다 — 붙어 있고 모양이 같은 두 물체를 분리하지 못하는 문제이지
`오른쪽` 이라는 단어의 문제가 아니다(오른쪽 장갑은 멀쩡했다).

**프롬프트로는 안 된다.** 지킬 수 있는 규칙은 자유변수를 왜곡해서라도 지키고, 지킬 수
없는 규칙(좌우 대칭 세로 범위 일치)은 조용히 무시했다. 문구를 더 얹는 3차 시도는 하지 말 것.

### 2026-09-03 실측 — 아핀 보정은 폐기했다

저장된 원본(`Swordman_Male_01.png`)을 픽셀로 쟀다. **API 비용 0.**

| | 실측 | 모델 | 차이 |
|---|---|---|---|
| 인물 맨 위(머리카락) | 0.0282 | 0.025 | −0.003 |
| 신발 맨 아래 | 0.9955 | 0.985 | −0.010 |

**양 끝이 1% 안쪽으로 맞는다.** 전역 이동이면 양 끝이 같은 방향으로 같은 양만큼
틀려야 하고, 전역 배율이면 위는 맞고 아래만 크게 틀려야 한다. 둘 다 아니다.
`y × 0.935/0.995` 를 실제로 넣어 봤고 되돌렸다(`ba0a1f9` → `698e384`).

0.935 라는 숫자 자체가 틀렸다. 그것은 도커 초기화 전 다른 실행에서 나온 값이고,
이 이미지의 인물은 0.9955 까지 내려온다. **재지 않고 쓴 상수였다.**

**틀리는 것은 긴 파츠의 높이다.** 오버레이를 그려 보면 밀린 게 아니라 짧다.

- 상의 0.135~0.370 — 파란 코트 자락은 0.55 까지 내려온다
- 하의 0.375~0.765 — 바지는 0.85 까지 간다
- 머리·신발은 오히려 잘 맞는다

파츠 하나하나의 참값은 **못 쟀다.** 인물에서 "상의"만 떼어내는 분할이 필요한데
흰 배경 대비로는 옷 경계가 안 나온다. 위 표는 인물 전체의 위·아래 끝 두 개뿐이고,
나머지는 오버레이를 눈으로 본 판단이다.

### 대칭 파츠(#3·#4·#9·#10)는 프롬프트로 하지 않는다

모델러는 장갑·신발·칼·팔꿈치 아래가 좌우 같은 디자인이니 한쪽만 만들면 된다고 했다.
**이것을 Extract 프롬프트 규칙으로 만들려던 계획을 폐기했다.**

좌우가 같은 캐릭터가 있고 다른 캐릭터가 있다. "장갑은 1개" 같은 규칙을 문면에 박으면
좌우가 다른 캐릭터를 망가뜨린다. 모델에게 "같은 디자인인지 판단해서 합쳐라"를 시키는
것도 안 된다 — #2 오른팔 스카프나 #8 오른쪽 발목 가드처럼 미묘한 비대칭을 놓치면
그 차이가 조용히 사라진다.

**그리고 그 환경은 이미 있다.** 검수 게이트가 이미지 생성 **전**에 걸리고, 거기서
파츠를 지울 수 있다(`RemoveReviewPartHandler` → `DELETE /api/jobs/{jobId}/review/parts/{partId}`
→ `reviewApi.removeReviewPart` → `ReviewGate` → `CharacterStudioScreen.tsx:426`).

- 좌우 같은 디자인 → 검수에서 오른쪽 파츠를 지운다 → 한쪽만 생성(어느 쪽이든 무관)
- 좌우 다른 디자인 → 그대로 둔다 → 양쪽 각각 생성

캐릭터마다·파츠마다 사람이 정한다. **코드 변경 없음.**

따라서 Extract 의 `Left and right sides of the same item are cut the same way and get
the same number of segments.` 는 **그대로 두는 것이 맞다** — 양쪽을 다 뽑아줘야 사용자가
검수에서 뺄 수 있다.

곁다리로 확인한 것: `PartHint.Count` 는 **배치(placements) 개수**지 생성 개수가 아니다
(`ValidateCharacterInput` 이 도메인 배치 규칙과 같은 1~20 으로 막는다). Extract 가 이 값을
안 읽는 것도 맞다. "Extract 가 개수 힌트를 무시한다" 는 진단은 틀렸다.

### #1 · #2 · #5 · #8 — 2026-09-08 실측으로 종결

골든셋은 9/2 같은 원본(`Swordman_Male_01.png`)·같은 힌트로 4번 실행됐고 끝까지 생성된
것은 `03900D2A` 하나다. 힌트: 몸통·머리·머리카락(짧은머리)·상의·하의·신발(무릎형)·무기
2·목걸이·귀걸이·장갑(팔꿈치형). 정본은 `LlmCalls.RequestPayload`·`ResponsePayload`(§함정 6).

**공통**: 4건 모두 전송 프롬프트에 벨트·관절 분할·갑주 자동 분리·힌트 스코프 규칙이 실제로
있었다. 파츠 수는 25~30개라 40개 상한과 무관하다. 코드에는 힌트 필터도 상한도 없다

**#1 벨트**: 원본은 2단(별 버클 벨트 + 메달 4개 벨트)이다. Extract 는 벨트·벨트 버클·벨트

미확정이다. **범위 밖으로 둔다.**

**#2 오른팔 스카프**: 원본은 상완의 주황색 천 매듭이다. 파츠가 없다. "오른쪽 장갑 팔꿈치
위" 서술이 "찢어진 갈색 천 장식" 으로 흡수했다 — 색까지 틀렸다. 원인은 택소노미에 스카프
타입이 없어 힌트로 켤 수 없고, 스코프 규칙("힌트에 없는 타입은 넣지 마라")이 배제하는
것이다. **결정: 사람이 검수에서 상자로 명시한다(A). 택소노미 추가(B)는 보류한다. 자동
분리(③)는 하지 않는다 — 매듭·붕대의 볼륨 경계는 모델러 판단 영역이다.**

**#5 벨트 아래 스커트**: 원본은 벨트 아래로 내려온 청색 천 자락이다. 상의 이미지(짧은
조끼)에도 하의 이미지(바지)에도 없다 — 완전히 사라졌다. 상의 서술이 "짧은 재킷" 으로
자락을 빼고 썼다. 원인은 #2 와 같다(택소노미에 자락 타입 없음 + 스코프 규칙이 옷 카테고리
발명을 금지한다). **결정: #2 와 같다.**

**#8 오른쪽 발목 가드**: 원본은 발목에 따로 스트랩으로 고정된 가죽·금속 가드다. "오른쪽
신발 발목 아래" 에 흡수됐다 — 서술은 "발목 갑주와 단단히 연결된다", 이미지는 갑주가 붙은
부츠 한 덩어리다. 원인은 갑주 자동 분리 규칙이 "상의·하의 위 갑주" 만 명시한 데 있다.
**결정: armor-any-region ① — 규칙을 "힌트된 어떤 파츠 위에 스트랩·버클로 따로 고정된
강체" 원리로 확장했다(Extract v13). 몸체가 판인 부츠는 분리 대상이 아니라는 반례를 같이
뒀다.**

**부수 발견 1**: 하의 이미지에 허벅지 스트랩이 그려졌다 — 별도 파츠 "오른쪽 허벅지 갑주"
와 중복이다. 하의 Generate 프롬프트에 벨트 제외 문구는 있었고 갑주 제외 문구는 없었다.
Generate 는 원본 이미지를 첨부받으므로 "원본에 보여도 그리지 마라" 반례가 있는 벨트·
머리카락만 지켜졌다. **결정: armor-any-region ②-3 — 반례를 "이 파츠 서술에 없는 겹침
표시는 그리지 않는다" 로 일반화했다(Generate v9).** (#6 은 모델러가 "붙어도 분리돼도
좋다" 로 닫았으므로 그 판정은 유지한다.)

**부수 발견 2**: 검수에서 "무릎 위"·"팔꿈치 위" 세그먼트 4개가 삭제된 채 생성됐다
(`IsManuallyAdded` 추가는 0건).

**원칙 (사용자 결정 2026-09-08)**: 자동은 초안이고, 검수에서 사람이 그린 상자가 정본이다.
본체는 ②다 — 사람이 그린 파츠가 이름·좌표·힌트대로 서술·생성되고, 겹치는 기존 파츠
이미지에서 그 영역이 빠진다(Rewrite v4 에 partHints, Decompose v12·Generate v9 의 관절 캡
규칙을 "리그가 굽히는 어떤 관절" 로 일반화하고 비관절 부위는 판 형태를 유지한다). ①은
상자 그릴 일을 줄이는 보조다. 과분리는 검수에서 삭제 한 번이고, 미분리는 상자·이름·
재작성을 기다리는 과정이라 과분리가 싸다.

스펙: `docs/specs/2026-09-08-armor-any-region.md` v2. 커밋: 스펙 `b980f12` → 문면 `3c45d84`
→ 재시드 `82844c8`. (82844c8 제목의 "RewriteDescriptions v5" 는 오기 — DB Version 은 4,
4350e26 에서 정정.)

**남은 것**: 실 API 재검증(사용자 결정, 약 ₩20,000) — 자동으로 발목 갑주가 분리되는지 /
검수에서 팔 스카프 상자를 추가하면 서술이 부위·색을 맞게 쓰는지 / 부츠 이미지에 가드가
없는지 / 하의에 허벅지 스트랩이 없는지 / 어깨 갑주는 여전히 캡인지 / 허벅지 갑주는
판인지. 그 전까지는 "시드됨" 이지 "해결됨" 이 아니다(workstream O 교훈).

### 칼 날 두께 — 모델러 마감으로 종결

아래 §3 참고. 4방향 뷰로는 얇은 강체의 두께를 못 만든다. 파이프라인을 분기시키지 않고
모델러가 두께를 준다.

## 모델러 컨펌이 필요했던 것 (2026-09-03 · **세 건 모두 종결**)

### 1. ~~손을 별도 파츠로 뽑을 것인가~~ → 뽑지 않는다 (#13)

지금은 파츠 목록에 **손이 없고**, 손을 `장갑 손목 아래` 가 그린다.

```
왼쪽 장갑 손목 아래
  "…검은 가죽 장갑과 손. 갈색 피부색이 일부 드러나는 관절 …
   손과 손가락의 실루엣을 완성한다."
베이스바디
  "각 의상과 장비가 차지하는 부위는 제외하고 …"
```

**일관되긴 하다** — 손목 아래를 장갑이 덮으니 장갑이 손을 맡았고, 빼면 손이 어디에도
없다. 원인은 관절 단위 이름(workstream M)이 만드는 `손목 아래` 구간의 알맹이가 곧
손이라는 데 있다. 이름은 장갑인데 내용물은 손인 파츠가 생긴다.

~~**물어볼 것**: 맨손을 별도 파츠로 두고 장갑을 껍데기로 뽑는 편이 리깅에 유리한가,
아니면 지금처럼 장갑이 손을 포함하는 편이 나은가.~~

**답 (2026-09-03 모델러 #13)**: 장갑에 손가락이 포함되어 생성되어도 좋다. 맨손을 별도
파츠로 뽑지 않는다. **현행 유지 — 코드 변경 없음.**

### 3. ~~얇은 물체가 두께 없이 면으로만 나온다~~ → 모델러 마감으로 종결

검·칼처럼 날이 있어야 하는 것이 평평한 면으로 나온다. 4방향 이미지가 전부 같은
납작한 실루엣이라 3D 재구성이 두께를 만들 근거를 못 받는다.

**벨트 장식처럼 얇은 것은 제대로 나온다**는 관측이 있어, 얇다는 것 자체가 원인은
아닌 듯하다. 조사 안 했다.

**떠올린 대안**: 칼 같은 물체만 입력 이미지를 2장(정면·측면)으로 줄인다. 다만 위
관측 때문에 우선순위가 낮다 — 먼저 왜 어떤 얇은 것은 되고 어떤 것은 안 되는지부터
봐야 한다.

**결정 (2026-09-04)**: **모델러가 두께를 준다. 파이프라인을 분기시키지 않는다.**

원인은 프롬프트 문면에서 보인다. `GenerateCharacterTail` 이 강체의 resting orientation 을
네 뷰에서 동일하게 유지하고 수직축으로만 카메라를 돌리라고 한다. 칼을 세워두면 좌·우
뷰는 날 두께만 보이는 거의 선에 가까운 실루엣이 되는데, 같은 문면이 `the silhouette and
visible surface area must visibly change` 도 요구한다. 모델 입장에서 "거의 아무것도 없는
이미지" 는 실패한 출력이고 학습 분포에도 거의 없다. 그래서 알아볼 수 있는 칼 형태를
네 번 그린다.

**workstream O 와 같은 실패 구조다** — 모델이 자기 사전확률("칼은 칼처럼 보인다")을
건드리지 않고 자유변수를 움직인다. 프롬프트로 이기려는 시도를 하지 말 것.

대안 (a) 측면을 3/4 로 트는 것은 카메라 동일 유지와 충돌해 조립 정합을 깬다. (b) 얇은
강체만 2뷰로 줄이는 것은 코드 분기가 필요한데, 위 §벨트 장식 관측 때문에 "얇음" 판정
기준을 아직 만들 수 없다. 칼은 모델러가 만들기 가장 쉬운 물건이라 (c) 를 택했다.

### 2. ~~손 자세를 펴야 하는가~~ → 반영 완료 (Generate v8)

자세 정규화 규칙 셋 중 **손에 걸리는 것이 없다.**

| 규칙 | 대상 |
|---|---|
| A-포즈 | 베이스바디일 때만 |
| A-포즈에 맞춘 재단 | 의류(상의·하의·겉옷·원피스) |
| 눕혀서 그리기 | 무기·도구 등 강체 |

장갑은 강체도 의류 목록에도 없어서 모델이 원본 포즈를 그대로 받아쓴다 — 원본이 검을
쥐고 있으니 `손잡이를 강하게 쥔 반폐쇄 주먹 형태` 가 나왔다. **규칙 공백이지 모델
잘못이 아니다.**

이쪽은 프롬프트 한 줄로 해결된다. workstream O 와 성격이 다르다 — O 는 모델에게
**측정**을 시켜 실패했고, 이것은 **자세를 지정**하는 것이라 A-포즈 규칙이 이미
통하고 있는 종류다. 다만 1번 결정에 따라 대상이 달라지므로 함께 정한다.

**반영 (2026-09-04, Generate v8)**: 1번이 "장갑이 손을 포함한다" 로 닫혔으므로 대상은
손목 아래 장갑 세그먼트다. 다섯 손가락을 모두 펴고 손가락 사이를 벌린 리깅 자세를
못박았고, **원본이 그 손을 어떻게 잡고 있든 무시한다**는 문장을 함께 넣었다 —
주먹이 나온 원인이 원본의 검 쥔 손을 받아쓴 것이기 때문이다.

## 환경 (2026-09-02 기준)

- **Docker 를 초기화했다.** 디스크가 100% 차서 VM 이 죽었고, VM 디스크 상한이 호스트 전체
  크기(228GB)로 열려 있던 것이 원인이었다. 설정에서 상한을 줄여둘 것.
- 그래서 **DB 가 비었다.** 공급자 키를 `/admin/providers` 에서 다시 등록해야 실행된다.
- 스택 기동: `deploy/local-up.sh` → `kubectl -n noxtend port-forward svc/api 18080:8080` →
  `apps/frontend` 에서 `pnpm dev`. 자세한 것은 README §로컬 실행.
- 마이그레이션 47개가 새 DB 에 전부 적용됐고, 프롬프트 M·N 이 활성이다.

## 이 브랜치에서 배운 함정 (재발 방지)

테스트로 고정해뒀지만 사람도 알고 있어야 하는 것들.

1. **프롬프트 문자열만 고치면 이미 적용된 DB 는 옛 문구를 쓴다.** 시드는 INSERT 한 번이고
   마이그레이션은 재실행되지 않는다. 반드시 재시드 마이그레이션을 함께 넣는다.
2. **마이그레이션을 손으로 쓰면 EF 가 무시한다.** `.Designer.cs` 와 `[Migration]` 속성이
   없으면 빌드·테스트는 초록불인데 DB 에는 아무것도 안 들어간다.
   → `MigrationRegistrationTests` 가 잡는다.
3. **구조화 출력 strict 모드는 `properties` 의 모든 키가 `required` 에 있어야 한다.**
   빠지면 400 이고, 그 실패는 재시도 대상이 아니라 작업 전체를 죽인다.
   → `SchemaListsEveryPropertyAsRequired` 가 잡는다.
4. **프롬프트 note 는 500자 이내.** 넘으면 마이그레이션이 죽어 API 가 안 뜬다.
   → `NoteFitsTheColumn` 이 잡는다.
5. **`FakeLlmProvider` 는 스키마도 프롬프트 문면도 검사하지 않는다.** 위 3·4 는 실 API 에서만
   드러난다.
6. **프롬프트 버전 히스토리는 DB 에 남지 않는다.** 시드 마이그레이션이 옛 문구를
   박아 두지 않고 `SeedPrompts.CharacterDecompose()` 를 부른다 — 그 마이그레이션이
   **실행되는 시점의 소스 코드**를 읽는다. DB 를 새로 만들면 마이그레이션 10개가
   전부 같은(그때 배포된) 문구를 넣어, 관리자 화면의 버전 목록이 열 줄인데 내용은
   한 벌이다. 실제로 2026-09-02 도커 초기화 뒤 `Character/Decompose` v1~v10 이
   전부 동일해졌다.
   → **옛 문구가 필요하면 git 에서 꺼낸다**:
   `git show <마이그레이션 커밋>:apps/backend/Noxtend.Infrastructure/Llm/SeedPrompts.cs`
   → **어느 프롬프트로 실행됐는지**는 `LlmCalls.RequestPayload` 가 정본이다. 보낸
   원문이 통째로 들어 있다. `PromptVersions` 는 그 근거가 못 된다.

7. **텍스트 단계는 워커가 1대다**(`TaskWorkerRegistration.cs`). 호출 하나가 늦으면 그 단계
   전체가 막힌다. 큐 회수가 무효라(§queue-reclaim 스펙) 지금은 재시작 외에 풀 방법이 없다.
