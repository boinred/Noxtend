# 미니 스펙: review-gate (검수 게이트)

## 배경 — 왜 지금 이 형태인가

`character-studio.plan.md` D-07이 검수 게이트를 범위 밖으로 미룬 이유는 "캐릭터만 예외로
오케스트레이터를 멈추면 `백본은 카테고리를 모른다`는 공유 전제가 깨진다"는 것이었다.
D-07 본문이 이미 대안을 제시한다: 카테고리 분기가 아니라 **접수 시점 per-job 플래그**
(`ProducesMeshes`와 같은 패턴)로 표현하면 전 카테고리에 적용해도 그 전제가 깨지지 않는다.
이 스펙은 그 대안을 택한다 — 캐릭터 전용이 아니라 **전 카테고리 opt-in 플래그**로 만든다.

## 파이프라인 상 위치

검수 게이트는 기존에 있던 두 시점(①접수 시 파츠 힌트, ②Decompose의 VLM 자동 좌표 산출)과
다른 **세 번째 시점**이다. ①은 아직 원본 이미지 위에 그릴 대상이 없어 좌표를 못 준다(체크박스
선언만 가능). 좌표는 ②가 실제로 파츠를 찾아낸 뒤에야 사람이 "빠졌다/틀렸다"를 눈으로 비교할
수 있으므로, 사람이 그리는 시점은 ②가 끝난 직후로 못박는다.

```
접수(①힌트, 좌표없음) → Analyze → Extract → Decompose(②VLM이 좌표 산출)
                                                    │
                                          [PendingReview] ← 여기서 사용자가 그린다
                                          (②의 결과를 보면서 빠진 것만 추가/틀린 것 삭제)
                                                    │
                                            전체 승인 → Generate 팬아웃
```

## 목표 (한 문장)

Decompose 직후 자동으로 Generate를 팬아웃하는 대신, `RequiresReview=true`로 접수된 작업은
사용자가 탐지된 파츠를 확인·추가·삭제하고 **한 번의 전체 승인**으로만 Generate를 트리거하게
만들어, 탐지 오류가 이미지 생성까지 조용히 통과하는 현재 한계(D-07-1)를 이번 범위에서만 줄인다.

## 입력 → 출력

**입력 예시** — 작업 접수 시:
```json
POST /api/jobs
{ "category": "Character", "uploadId": "...", "providerConfigId": "...", "model": "...",
  "requiresReview": true }
```

Decompose 완료 후 검수 대기 상태에서 조회:
```json
GET /api/jobs/{jobId}/review
→ {
    "status": "PendingReview",
    "parts": [
      { "partRef": "P01", "name": "허리띠", "placements": [{"x":0.3,"y":0.6,"w":0.05,"h":0.08}],
        "source": "detected" }
    ]
  }
```

편집 (추가/삭제는 각각 별도 호출, 즉시 반영 — 승인 전까지는 초안 상태):
```json
POST /api/jobs/{jobId}/review/parts        # 추가 — 사각형 좌표 + 이름 + 카테고리
DELETE /api/jobs/{jobId}/review/parts/{partRef}   # 삭제(제외)
```
`x,y,w,h`는 사용자가 숫자로 입력하지 않는다. 화면에 렌더된 원본 이미지 위에서 드래그로
사각형을 그리면 픽셀 좌표가 잡히고, 프론트가 이미지 실제 가로세로로 나눠 0~1 비율로
정규화한 뒤 위 API로 보낸다(`Bounds`/`Placements`가 이미 쓰는 좌표계와 동일).

새 박스가 기존 파츠 중 하나와 좌표상 조금이라도 겹치면(단순 교차 — IoU 임계값 아님,
§예상 함정 6 참고) 추가 자체를 거부한다:
```json
POST /api/jobs/{jobId}/review/parts
{ "name": "벨트", "category": "Belt", "bounds": {"x":0.28,"y":0.55,"w":0.44,"h":0.1} }
→ 400 { "error": "PartOverlapsExisting", "conflictsWith": ["P03"] }
```

**출력 예시** — 전체 승인:
```json
POST /api/jobs/{jobId}/review/approve
→ 202 { "status": "Running", "generateTasksPlanned": 7 }
```
승인된 파츠 수만큼 `Generate` 공정이 **한 번에** 팬아웃 계획되고, 오케스트레이터가
`EnqueueReadyTasksAsync`로 그대로 적재한다 (기존 팬아웃 경로 재사용, 신규 로직 없음).

## 이번에 안 하는 것 (제외 범위)

- **개별 파츠 부분 승인** — "이 파츠만 지금 생성"은 안 한다. 병렬 파츠 공정이 검수 도중
  파츠 목록이 바뀌는 것과 경합해 겹쳐 생성될 수 있다(사용자가 지적한 문제). 전체 승인
  단일 트리거만 만든다.
- **재탐지** — 승인 화면에서 "다시 분석해줘" 버튼. 이번엔 기존 탐지 결과 위에서 사람이
  더하고 빼는 것까지만.
- **사각형 실시간 미리보기 생성** — 제외하는 건 "이 박스로 생성하면 결과물이 어떻게
  나올지" 크롭 미리보기를 만드는 것뿐이다. 드래그로 그리는 동안 박스 테두리가 원본
  이미지 위에 겹쳐 보이는 것(라이브 아웃라인)은 당연히 기본 UI로 포함 — 그게 없으면
  사용자가 자기가 그린 사각형의 크기·위치를 눈으로 확인할 방법이 없다. Label Studio의
  bbox 도구가 이 구분의 참고 사례다: 드래그하면 박스 테두리와 좌표가 실시간으로
  갱신되고 이후 x/y/w/h를 숫자로 미세조정할 수 있지만, 그 박스 영역을 잘라 별도
  미리보기 이미지로 렌더링하는 기능은 없다(labelstud.io/tags/rectanglelabels,
  labelstud.io/templates/image_bbox). 좌표 검증(프레임 안쪽 여부)은 별도로 한다.
- **기존 진행 중/완료 작업 소급 적용** — opt-in 플래그라 신규 작업부터만 해당.
- **3D·조립 단계 연동** — 이미지 파츠 검수까지. `character-studio` D-09와 같은 경계.
- **동시 편집 잠금(협업)** — 같은 작업을 두 탭에서 동시에 검수하는 상황의 낙관적 동시성
  제어는 함정 목록(§예상 함정)에서 발견만 하고, 처리(버전 필드·409)는 구현 단계에서 설계.

## 예상 함정

1. **스위퍼가 검수 대기 작업을 자동으로 넘긴다.** `PipelineJob.IsReadyToRun`이 검수 상태를
   모르면, `TaskSweeper`가 기존처럼 Decompose 직후 Generate를 자동 계획해버려 검수 게이트가
   무력화된다. `IsReadyToRun`(또는 팬아웃 트리거 지점)이 `RequiresReview && Status ==
   PendingReview`일 때 명시적으로 대기해야 한다 — D-07이 경고한 "판정이 두 곳에 흩어지면
   스위퍼가 어긋난다"는 실제 전례(part-generation.design.md §1.2)가 있다. **Decompose task가
   Succeeded로 기록되는 시점과 Job.Status가 PendingReview로 바뀌는 시점은 같은
   `ReconcileFromTasks` 호출(같은 트랜잭션) 안에서 원자적으로 처리해야 한다** — 별도 API나
   비동기 알림으로 분리하면 그 틈에 스위퍼 폴링이 끼어들어 게이트가 무력화될 수 있다.
2. **좌표 검증 누락.** 사용자가 그린 사각형이 프레임 밖이거나 w/h가 0에 가까우면 Generate
   입력이 무의미해진다. `AssetPart`/`Bounds`가 이미 가진 `IsWithinFrame` 규칙을 편집 API에도
   그대로 적용해야 한다(따로 만들지 않는다).
3. **수동 추가 파츠의 서술 공백.** VLM이 만든 파츠는 `description`이 채워져 있지만 사용자가
   사각형만 그려 추가한 파츠는 이름 외 서술이 빌 수 있다. Generate 프롬프트가 서술을
   필수로 쓰면 빈 문자열이 그대로 들어가 화풍이 흔들린다 — 최소 입력(이름+카테고리) 이상을
   요구하거나, 빈 서술을 좌표만으로 보완하는 프롬프트 문구가 필요하다.
4. **승인 후에는 여전히 D-07-1 한계가 유지된다.** 승인해서 Generate가 실패하거나 결과가
   이상해도, 검수 화면을 다시 열어 고치는 경로는 이번 스펙에 없다(제외 범위). 사용자가
   "승인 취소하고 다시 검수"를 기대하면 안 되는 지점을 화면 문구로 명확히 해야 한다.
5. **동시 편집 경합.** 같은 job을 두 세션에서 열면 나중 승인이 앞선 편집을 덮어쓸 수 있다.
   최소한 승인 시점에 "마지막으로 읽은 파츠 목록 버전"을 함께 보내 어긋나면 409로 막는
   낙관적 동시성 체크가 필요하다. **이번 스펙에서는 구현하지 않기로 확정(2026-08-30)** —
   검수 담당자가 1인이라 같은 job을 두 세션에서 동시에 여는 상황 자체가 현재 운영에서
   발생하지 않고, 지금 만들면 실사용 없는 방어 코드가 된다(오버엔지니어링). 검수 인원이
   여러 명으로 늘어나는 등 운영 방식이 바뀌면 그때 이 함정을 다시 꺼내 구현한다 — 코드
   변경 없이 이 함정 항목만 남겨서 재검토 지점을 표시해둔다.
6. **수동 추가 파츠는 기존 파츠와의 겹침(occludedBy)이 계산되지 않는다 — 미해결, 별도로
   다듬는 중.** 지금 Generate가 벨트/바지 같은 겹침을 안 그리는 이유는 Decompose가 파츠
   전체를 한 번에 보고 `occludedBy`와 "그걸 뺀 description"을 같이 산출하기 때문이다
   (`SeedPrompts.cs:702` 부근). 사람이 나중에 사각형 하나만 그려 파츠를 추가하면 이 판단이
   비게 되어, 기존 파츠(예: 바지)는 여전히 벨트를 포함해 그려지고 새로 추가한 벨트 파츠도
   따로 그려져 **내용이 중복(겹쳐서) 생성**된다. 박스 좌표 하나만으로는 못 고친다 — 최소한
   "새 박스와 좌표가 겹치는 기존 파츠들"을 묶어 Decompose를 다시 태워 occludedBy·description을
   같이 갱신해야 하는데, 겹침을 뭘로 판정할지(좌표 교차? 사용자 수동 지정?)가 아직 안 정해졌다.
   **이번 스펙이 결정한 경계선:** occludedBy 재계산 자체(가리는 파츠의 description을
   다시 산출하는 것)는 여전히 다음 스펙으로 미룬다. 대신 **"겹치는 추가를 막는다"는 완화책은
   이번 범위에 포함**하고, 겹침 판정은 아래 리서치 메모가 제시한 규칙을 그대로 채택한다 —
   새 박스가 기존 파츠 하나와 좌표상 조금이라도 겹치면(intersection > 0, IoU 임계값 아님)
   `POST review/parts`를 400으로 거부한다(예시는 §입력→출력). "완전히 빠뜨린 독립 파츠
   추가"만 통과하므로, 벨트처럼 기존 파츠와 겹치는 파츠를 사람이 수동으로 추가하는
   경로는 **이번 스펙에서는 막혀 있다** — 화면 문구로 "겹치는 파츠는 다음 업데이트에서
   지원 예정"임을 명확히 안내해야 한다(사용자가 버그로 오인하지 않도록).

   **부작용 (2026-08-30 발견):** 이 guard는 D-07-1이 애초에 풀려던 "탐지 오류를 사람이
   교정할 수 있게 하자"는 목표의 일부를 다시 막는다. VLM이 벨트를 잘못 감지했거나 아예
   놓쳐서 검수자가 기존 파츠를 지우고 올바른 위치에 다시 그리려 할 때, 그 올바른 위치가
   옆 파츠(바지 등)와 겹친다면 이 guard가 그 교정 자체를 400으로 거부한다 — "탐지가
   틀렸는데 고칠 수도 없는" 상황이 생길 수 있다는 뜻이다. 이번 스펙은 이 트레이드오프를
   감수하고 승인받는다: 겹치는 위치의 오류 교정은 다음 스펙(occludedBy 재계산)이 나올
   때까지 지원되지 않는다. 화면 문구에도 "탐지 오류가 겹치는 위치라면 지금은 고칠 수
   없다"는 점을 함께 안내해야 한다.

   **다음 스펙 착수자를 위한 메모:** 겹침 제한을 풀고 실제로 occludedBy를 재계산하려면
   "새 박스와 교집합인 기존 파츠들만 묶어 Decompose 재실행"이 유력한 접근인데, 이는
   `PipelineJob.ValidatePartDetails`(응답 파츠 수가 기존 `_parts`와 정확히 1:1 이름 일치해야
   한다는 불변식)와 충돌한다 — 이 불변식을 부분 집합 응답도 허용하도록 완화하거나, 재계산
   결과를 기존 파츠 목록에 병합하는 별도 경로를 새로 만들어야 한다. 다음 스펙은 이 지점부터
   시작한다.

   **리서치 메모 (2026-08-29, 직접 조사 + Gemini 교차검증):**
   - 겹침 판정 기준 — 실무 도구는 대부분 자동 IoU 감지를 안 쓴다. CVAT은 occlusion/z-order를
     사람이 수동으로 지정하는 속성으로 다루고, IoU는 어노테이터 간 라벨 일치도(QA)에만 쓴다 —
     서로 다른 두 객체가 실제로 겹치는지 판정하는 용도가 아니다(Gemini가 이 둘을 혼동해 인용한
     CVAT 문서 URL은 404로 확인됨 — 해당 주장은 폐기). 유일하게 구체적 규칙을 제시한 선행
     사례는 BBBD 논문(arxiv.org/abs/2204.12841): 두 박스의 IoU 임계값이 아니라 "교차 영역이
     존재하는가(intersection > 0)"만으로 겹침을 판정하고, 그 교차 영역 안의 세그멘테이션
     마스크로 depth order를 복원한다. 벨트-바지처럼 크기 차이가 큰 파츠 쌍은 IoU 값 자체가
     항상 낮게 나오므로, IoU 임계값 방식은 우리 문제에 안 맞고 단순 좌표 교차 여부가 맞다.
   - 재계산 범위 — Incremental Scene Graph Generation 계열 선행 사례는 새 노드 추가 시
     전체 씬이 아니라 공간적으로 교차하는 이웃 노드들과의 관계만 국소적으로 재추론한다.
     이는 앞서 세운 가설("새 박스 + 좌표가 겹치는 기존 파츠들만 묶어 재-Decompose")과 일치.
   - CVAT 선례가 시사하는 대안: 자동 판정 없이 "사람이 겹침을 명시적으로 지정"하는 것도
     업계 표준이다. 좌표 교차 자동 감지 + 사람이 확정하는 하이브리드가 실무에서 흔한 패턴.
   - 결론은 아니다 — 다음 스펙에서 이 메모를 출발점 삼아 판정 기준·재계산 범위를 확정한다.
   - **"겹치는 추가 막기" guard 자체의 단순성 재검토 (2026-08-30):** intersection>0 판정은
     사각형 두 개의 가로/세로 구간이 겹치는지 보는 boolean 한 줄로, 이미 가장 단순한 형태다.
     IoU 임계값·세그멘테이션 마스크 기반 판정·사람 수동 선언 같은 대안은 이 규모의 guard엔
     오히려 과하다(마스크 기반은 이 파이프라인에 없는 세그멘테이션 인프라가 필요, 수동
     선언은 검수자가 깜빡하면 안전장치가 무력화됨) — §함정5(동시 편집 잠금 제외)와 같은
     "실사용 없는 방어 코드를 만들지 않는다"는 원칙에 비춰, 지금보다 더 단순화할 수도
     없고 더 정교하게 만들 이유도 없다고 판단해 intersection>0을 그대로 채택한다.
7. **"전 카테고리 opt-in 플래그로 안전하다"는 검증되지 않았다.** `PipelineJob` 주석은 카테고리마다
   갈리는 것이 "공정 구성뿐"이라고 하지만, Extract/Decompose 조합이나 파츠 산출 방식이
   캐릭터와 배경/소품에서 실제로 동일한지 이 스펙은 확인하지 않았다. 카테고리별로 검수 화면이
   붙는 도메인 진입점이 다르거나, 함정 6(occludedBy)의 심각도 자체가 카테고리마다 다를 수
   있다(배경은 옷 가림 같은 관계가 약할 수 있음). 구현 착수 전 캐릭터 외 카테고리 1개로
   최소 E2E 1회를 §검증방법에 넣어 이 가정을 검증한다.

## 검증 방법

- 단위 테스트: `RequiresReview=true`로 접수한 작업이 Decompose 완료 후 `PendingReview`
  상태로 멈추고, Generate 공정이 하나도 계획되지 않았음을 확인.
- 단위 테스트: 프레임 밖 좌표(`x+w > 1` 등)로 파츠 추가 시 400/도메인 예외 반환.
- 단위 테스트: (§예상 함정 6) 기존 파츠와 좌표가 조금이라도 교차하는 박스로 파츠 추가 시
  `PartOverlapsExisting` 400 반환, 파츠 목록에 반영되지 않음. 교차하지 않는 박스는 정상 추가됨.
- 단위 테스트: (§예상 함정 3) 이름·카테고리만 넣고 서술 없이 파츠 추가 → 승인 → Generate
  프롬프트에 들어가는 description이 빈 문자열이 아니라 완화책(최소 입력 요구 또는 보완 문구)이
  적용된 값인지 확인.
- 단위 테스트: `POST .../approve` 호출 후 승인된 파츠 수 == 계획된 Generate 공정 수.
- 단위 테스트: 삭제한 파츠는 승인 목록에서 빠지고 Generate 공정도 안 생김.
- 회귀 테스트: `RequiresReview=false`(기존 동작)인 작업은 지금처럼 Decompose 직후
  자동으로 Generate가 팬아웃됨 — 검수 게이트가 옵트인이지 전면 교체가 아님을 확인.
- E2E (Character): 검수 화면에서 사각형으로 파츠 1개 추가 → 기존 파츠 1개 삭제 → 전체 승인 →
  결과 갤러리에 승인된 파츠 수만큼만 이미지가 생성됨을 확인.
- E2E (§예상 함정 7): 캐릭터 외 카테고리 1개(예: 배경)로 동일한 PendingReview → 승인 흐름이
  깨지지 않고 통과하는지 최소 1회 확인 — "전 카테고리 안전" 전제를 실증한다.
- (§예상 함정 6 관련) occludedBy 재계산 자체는 이번 스펙에서 해결책을 정하지 않았으므로
  검증 대상에서 제외한다 — 겹침을 "막는 것"은 위 400 테스트로 검증하지만, 겹침을 "허용하고
  올바르게 그리는 것"은 다음 스펙에서 판정 기준·재계산 범위가 정해지면 그때 테스트를 추가한다.
